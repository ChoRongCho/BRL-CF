# 2026-06-30 미팅 기준 논문 방향성과 TODO

## 1. 전체 방향

오늘 미팅 기준으로 논문 방향은 **planning 중심 시스템 논문**으로 잡는다. 사람에게 물어보는 시스템인 이상 유저 스터디는 필요하다. 현재 논문에서 핵심으로 볼 것은 task performance이다.

중심 metric은 다음이다.

- task success rate
- task completion time / operation time
- response time
- query count
- query ratio
- belief update 이후 task 진행 양상

workload, trust, fatigue, situation awareness 같은 human factor 분석은 이후 합류할 HRI 포닥 연구자가 별도 방향으로 맡는 것이 자연스럽다.

현재 논문의 중심 문장은 다음처럼 잡는다.

```text
부분 관측 환경에서 로봇은 planning에 필요한 정보를 스스로 식별하고,
query를 통해 task-relevant uncertainty를 줄이며,
그 응답을 belief update와 replanning에 반영한다.
```

## 2. 문제 정의

현실 환경의 로봇은 partial observability 때문에 hidden state를 완전히 알 수 없다. hidden state 추정이 틀리면 action 선택이 틀어지고, 그 결과 task performance가 떨어질 수 있다.

feedback source는 로봇이 직접 알기 어려운 정보를 제공할 수 있다. 그러나 질문은 비용이 있으므로, 로봇은 다음을 결정해야 한다.

- 언제 질문할 것인가
- 무엇을 질문할 것인가
- 어떤 형식으로 질문할 것인가
- 응답을 belief / knowledge update에 어떻게 반영할 것인가
- update 이후 어떻게 replanning할 것인가

PPT 기준 핵심 아이디어는 유지한다.

```text
현재 행동으로 도달 가능한 action frontier에서 uncertainty를 평가하고,
planning과 직접 관련된 uncertainty를 대상으로 query timing과 query content를 결정한다.
```

## 3. Contribution 방향

논문 contribution은 `When / What / How` 구조로 정리한다.

### 3.1 When: query timing

로봇이 partial observability 환경에서 현재 action 선택의 uncertainty를 정량화하고, feedback source의 도움이 필요한 시점을 판단한다.

볼 것:

- query 발생 시점
- query count
- query ratio
- task success rate
- task completion time / operation time

### 3.2 What: query content

로봇이 현재 planning에 필요한 state 또는 predicate를 식별하고, 이를 query 대상으로 선택한다.

볼 것:

- 어떤 predicate가 query로 선택되는지
- query answer가 belief update에 들어가는지
- belief update 이후 action selection이 바뀌는지
- task success rate
- task completion time / operation time

### 3.3 How: state-level query format

PPT 기준으로 `How`는 query를 belief update에 넣는 구현 방식만을 뜻하지 않는다.
핵심은 **어떤 형식으로 질문할 것인가**이다.

Ours는 불확실성을 action 단위가 아니라 state / predicate 단위로 질의한다.
즉 사용자의 피드백이 특정 state variable 또는 symbolic predicate에 대응되도록 만든다.

이 방식은 action-level query보다 planning에 더 직접적으로 연결된다.
행동 수준 질문은 로봇이 어떤 hidden state를 잘못 알고 있는지 명시적으로 잡지 못하지만,
state-level query는 잘못된 상태 인지를 belief / knowledge update로 바로 수정할 수 있다.

정리 문장:

```text
We formulate queries as state-level predicates so that feedback can directly
correct task-relevant belief under partial observability.
```

## 4. 실험 구성

### 4.1 유저 스터디의 위치

사람에게 물어보는 시스템이므로 유저 스터디는 필요하다. 이번 논문에서 유저 스터디는 task performance 확인에 가깝다.

유저 스터디에서 볼 것:

- 사람이 질문에 답했을 때 task success가 어떻게 되는지
- 사람이 답했을 때 task completion time / operation time이 어떻게 되는지
- query에 대한 response time이 어느 정도인지
- 질문 응답이 planning loop에 들어가 task 진행에 영향을 주는지

인터페이스 구현은 가볍게 가져간다. 자유로운 시뮬레이션 평가와 task performance 기록을 우선한다.

### 4.2 먼저 Oracle 실험

가장 먼저 해야 할 것은 Oracle 실험이다. 이때 핵심은 **Oracle / Human-Proxy / Human**의 역할을 분리하는 것이다.

Oracle은 항상 정답을 알고, goal까지 가는 heuristic information을 가진 존재로 정의한다. 따라서 Oracle 실험은 system upper bound를 확인하는 역할을 한다. 이후 Human-Proxy와 Human을 통해 실제 feedback source와의 연결성을 확인한다.

Oracle 실험에서는 다음을 고찰한다.

- Oracle이 GT hidden state를 알고 답하는 방식
- Oracle이 goal state까지 가는 heuristic information을 사용하는 방식
- Oracle answer가 belief update에 들어가는 방식
- Oracle answer 이후 replanning이 실제로 바뀌는지
- Oracle 실험 결과가 Human-Proxy / Human 응답에서도 비슷한 경향을 보이는지

핵심 질문:

```text
Oracle answer를 넣었을 때 task performance가 좋아지는가?
그리고 그 결과가 Human-Proxy / Human 응답을 넣었을 때도 비슷하게 나타나는가?
```

### 4.3 Feedback source 3축

오늘 미팅에서 가장 중요한 지점은 feedback source의 역할을 명확히 나누는 것이다. 세 축은 다음 세 단어로 정리한다.

```text
Oracle
Human-Proxy
Human
```

#### Oracle

Oracle은 planner가 생성한 질문에 대해 항상 정답을 알고 대답하는 존재이다. 여기서 정답은 GT hidden state와 질문 대상 predicate의 truth value를 포함한다. 또한 Oracle은 goal state까지 가는 heuristic information을 알고 있다고 둔다.

즉 Oracle은 다음 정보를 가진 feedback source이다.

- GT hidden state
- 질문 대상 predicate의 truth value
- object의 hidden property
- 현재 state에서 goal state까지 가는 heuristic information
- 어떤 응답이 task completion에 도움이 되는지에 대한 task-relevant direction

Oracle의 역할은 system upper bound를 보는 것이다. Oracle 결과가 좋으면, planner query와 belief update, replanning loop가 이상적인 feedback source 아래에서 작동한다는 것을 확인할 수 있다.

#### Human-Proxy

실제 사람은 화면, 이미지, 상태 설명, 질문 문장을 보고 응답한다. 따라서 Human-Proxy를 생각할 때는 다음 특성을 봐야 한다.

- 질문을 이해할 수 있는지
- 질문 대상 object/state를 식별할 수 있는지
- predicate에 대해 yes/no 또는 label 응답을 할 수 있는지
- 질문 유형에 따라 오류가 달라지는지
- 낮은 확신으로 답하는 경우가 있는지
- 같은 유형의 질문에서 응답이 흔들리는지

Human-Proxy는 실제 사람 응답에서 관찰 가능한 일부 특성을 반영한 feedback source이다. 현재 범위에서는 오류, 낮은 확신, 질문 유형별 흔들림 중심으로 둔다. response time은 유저 스터디 metric으로만 기록한다.

Human-Proxy는 VLM으로 구현할 수도 있고, 사람 응답 통계를 반영한 proxy model로 구현할 수도 있다. 핵심은 GT를 그대로 쓰는 Oracle과 실제 Human 사이의 중간 feedback source로 둔다는 점이다.

#### Human

Human은 실제 사람이 같은 planner query에 답하는 feedback source이다. 사람은 제공된 화면이나 설명을 보고 판단한다.

이 세 축은 다음처럼 정리한다.

```text
Oracle:
항상 정답을 알고, goal까지 가는 heuristic information을 가진 feedback source.

Human-Proxy:
VLM 또는 사람 응답 특성을 일부 반영한 approximate feedback source.

Human:
실제 사람이 화면, 이미지, 상태 설명, 질문 문장을 보고 답하는 feedback source.
```

### 4.4 왜 Human-Proxy가 중요한가

교수님이 Human-Proxy를 중요하게 본 이유는 Oracle 실험이 실제 human feedback setting과 연결될 수 있는지 판단해야 하기 때문으로 해석된다.

Oracle은 GT를 알고 항상 맞게 답하며, goal까지 가는 heuristic information을 가진다. 이 설정에서 결과가 잘 나오면 system의 upper bound는 확인할 수 있다. 하지만 사람에게 물어보는 시스템이라는 주장으로 연결하려면 추가 설명이 필요하다. reviewer는 다음 질문을 할 수 있다.

```text
좋은 결과가 나온 이유가 query / planning method 때문인가?
비현실적으로 강한 feedback source를 사용했기 때문인가?
```

따라서 feedback source의 의미를 나눠서 봐야 한다.

```text
Oracle:
항상 정답을 알고, goal-directed heuristic information을 가진 feedback source.
시스템이 이론적으로 잘 작동하는지 보는 upper bound.

Human-Proxy:
실제 사람이 줄 법한 답변 특성을 일부 반영하는 feedback source.
사람에게 물어보는 시스템으로서 현실성이 있는지 확인하는 장치.

Human:
실제 사람이 같은 planner query에 답하는 feedback source.
```

교수님이 말한 "사람과 유사한 oracle"은 세 축 중 Human-Proxy에 가깝다. Human-Proxy는 사람이 답할 수 있는 정보와 사람이 보일 수 있는 오류 특성을 일부 반영한 feedback source이다.

이 관점에서 내부 데이터 결과는 논문 작성 가능성을 판단하는 기준이 된다.

```text
Oracle에서만 잘 됨:
system upper bound는 보였지만, human-facing system claim은 약하다.

Human-Proxy에서도 잘 됨:
현실적인 feedback source에서도 query mechanism이 planning 성능에 기여한다.
planning 중심 system 논문으로 밀 수 있다.

Human-Proxy에서 잘 안 됨:
현재 query가 실제 사람이 제공할 수 있는 정보와 맞지 않을 가능성이 있다.
claim을 낮추거나 query 형식 / 실험 방향을 수정해야 한다.
```

즉, Human-Proxy의 목적은 "사람을 흉내낸 oracle을 만드는 것" 자체가 아니다. 핵심은 다음이다.

```text
우리 query가 실제 사람이 답할 수 있는 종류의 질문인가?
그 답변이 Oracle 실험과 같은 방향으로 task performance에 영향을 주는가?
```

따라서 실험은 다음 세 feedback source를 같은 task / 같은 query mechanism 위에서 보는 구조가 자연스럽다.

```text
1. Oracle
2. Human-Proxy
3. Human
```

이렇게 두면 Oracle은 upper bound, Human-Proxy는 approximate responder, Human은 actual feedback source로 해석할 수 있다. 세 source를 같은 task/query에서 놓고 success rate와 task 진행 양상을 보면, oracle 결과의 의미를 더 분명하게 설명할 수 있다.

## 5. 추가 실험

### 5.1 Active search / sensing baseline

추가 실험으로 active search 또는 sensing 기반 baseline을 고려한다.

이 baseline의 의미:

- 로봇이 직접 추가 탐색 또는 sensing을 수행한다.
- uncertainty를 줄이는 다른 information acquisition 방식으로 볼 수 있다.
- Ours의 state-level query와 비교할 수 있다.
- sensing / query action을 planning action space 안에 넣을 때 search space가 어떻게 커지는지 비교할 수 있다.

볼 metric:

- task success rate
- task completion time / operation time
- query count
- search count
- sensing count
- search / sensing cost

### 5.2 Ours 기준 비교

Ours는 query를 physical planning action으로 직접 넣지 않는다.
Query는 planning-relevant information acquisition이지만,
physical action space와 분리된 belief refinement step에서 수행한다.

핵심은 state-level predicate query다.

평가 관점:

- query가 belief update에 들어가는가
- belief update 이후 replanning이 바뀌는가
- query가 task success에 영향을 주는가
- query가 completion time / operation time에 영향을 주는가
- state-level query가 action-level query보다 잘못된 상태 인지를 더 직접적으로 수정하는가

## 6. 도메인 확장

도메인은 다양한 partial observability 도메인으로 확장하는 방향을 검토한다.

검토할 도메인:

- tomato harvesting
- waste sorting
- Blocksworld
- pick-and-delivery
- assembly
- household manipulation
- RoboCasa

도메인 확장의 원칙:

- 새 환경 구현 비용을 낮게 유지한다.
- 이미 있는 benchmark를 최대한 활용한다.
- hidden state 또는 hidden predicate가 있는 환경을 우선한다.
- query가 planning에 영향을 줄 수 있는 환경을 우선한다.
- task success rate와 operation time을 자동 기록할 수 있는 환경을 우선한다.

우선순위:

1. 현재 있는 tomato / waste sorting 정리
2. 기존 benchmark 중 partial observability를 만들기 쉬운 symbolic domain 검토
3. Blocksworld, pick-and-delivery, assembly 중 구현 비용이 낮은 도메인 확인
4. household manipulation / RoboCasa는 가능성 검토

## 7. 관련 연구 방향

관련 연구는 planning 중심으로 정리한다.

### 7.1 Planning under partial observability

볼 내용:

- POMDP
- POMCP
- belief update
- online planning
- symbolic planning under uncertainty

우리 위치:

```text
partial observability에서 task-relevant hidden state uncertainty를 유지하고,
query answer를 belief update와 replanning에 반영한다.
```

### 7.2 Active sensing / information gathering

볼 내용:

- active sensing
- active search
- value of information
- information gathering action
- sensing action in planning

우리 위치:

```text
query를 robot sensing과 유사한 information acquisition action으로 보고,
planning 성능에 주는 영향을 평가한다.
```

### 7.3 Human feedback / help-seeking systems

피드백 소스의 역할을 정의해야 한다.

관련 역할:

- expert demonstrator
- supervisor / human-on-the-loop operator
- corrective feedback provider
- help provider
- clarification respondent
- state / predicate verifier

우리 논문에서 feedback source는 다음 역할에 가깝다.

```text
planner-generated query에 대해
task-relevant hidden state 또는 symbolic predicate의 값을 응답하는 source
```

사람은 화면이나 설명을 보고 응답한다. Oracle은 GT hidden state와 goal-directed heuristic information을 사용해 응답한다.

### 7.4 LLM-based query / KnowNo

KnowNo류 방법은 action-level uncertainty가 있을 때 사용자에게 질문한다.

우리 방향:

- state / predicate-level uncertainty를 다룬다.
- 질문 형식은 state-level predicate query로 둔다.
- 답변은 belief update에 들어간다.
- update 이후 replanning이 수행된다.

볼 것:

- When: No / All / Random / Ours, threshold 변화

### Step 4. Human-Proxy 가능성 확인

작은 사람 응답 데이터 또는 VLM 응답을 통해 Human-Proxy에 넣을 수 있는 특성을 본다.

볼 것:

- 질문 이해 여부
- object/state 식별 여부

- 확신도

### Step 5. Feedback source 3축 실험

같은 planner, 같은 query mechanism, 같은 task set을 두고 feedback source만 바꿔 본다.

축:

- Oracle
- Human-Proxy
- Human

확인할 것:

- source별 task success rate

- source별 answer accuracy
- source별 belief update 이후 action 변화
- Oracle 결과와 Human-Proxy / Human 결과의 경향 차이

이 실험의 목적은 Oracle에서 보인 성능 경향이 Human-Proxy 또는 Human 응답에서도 의미 있게 유지되는지 보는 것이다.

### Step 6. Active search / sensing baseline

state-level query와 별도로 search 또는 sensing으로 uncertainty를 줄이는 실험을 검토한다.

기록할 것:

- task success rate
- operation time
- search / sensing count
- search / sensing cost
- belief update 이후 action 변화

## 9. System 논문 구조

PPT와 오늘 미팅을 합치면 system 논문은 다음 구조로 정리할 수 있다.

```text
문제 정의
관련 연구
방법
실험
```

### 9.1 문제 정의

- partial observability 환경의 robot planning
- hidden state uncertainty
- planner-generated query
- feedback source
- belief update
- replanning
- task performance 중심 평가

### 9.2 관련 연구

- planning under partial observability
- active sensing / information gathering
- human feedback / help-seeking systems
- LLM-based query / KnowNo
- feedback source 역할 정의

### 9.3 방법

방법 섹션의 중심 loop:

```text
state / knowledge / transition model
-> action frontier generation
-> uncertainty evaluation
-> query generation
-> feedback source response
-> belief / knowledge update
-> replanning
-> task execution
```

정리할 모듈:

- symbolic state / predicate representation
- action frontier
- uncertainty / entropy

## 10. Human-Proxy와 feedback source 설정의 의미

Human-Proxy의 목적은 사람 응답을 정교하게 재현하는 모델을 만드는 것이 아니다. 현재 논문의 중심은 planning system이다. 따라서 Human-Proxy는 Oracle 실험 결과가 실제 human feedback setting과 연결될 수 있는지 점검하기 위한 feedback source로 둔다.

핵심은 다음이다.

```text
Human-Proxy는 Oracle result의 해석 가능성을 점검하는
evaluation device이다.
```

교수님이 "사람과 유사한 Oracle"을 중요하게 말한 이유도 이 관점에서 이해할 수 있다. Oracle은 GT hidden state와 goal heuristic을 알고 항상 정답을 준다. 이 결과가 좋게 나와도, reviewer는 feedback source가 강해서 나온 결과인지 query planning method가 의미 있게 작동한 결과인지 물을 수 있다.

따라서 Human-Proxy는 다음 질문을 보기 위한 장치이다.

- Oracle assumption을 낮췄을 때도 planning benefit이 유지되는가
- planner가 만든 query가 사람이 답할 수 있는 종류의 질문인가
- 사람이 제공할 수 있는 정보가 belief update와 replanning에 들어갈 수 있는가
- feedback source가 완벽하지 않아도 task success 경향이 유지되는가
- Oracle 결과를 human feedback setting의 주장으로 연결할 수 있는가

현재 범위에서 response time은 Human-Proxy 모델에 넣지 않는다. response time은 user study에서 기록하는 task performance 관련 metric으로만 둔다. `unknown` 응답도 의미적으로는 중요하지만, 현재 Human-Proxy 설정에는 포함하지 않는다.

### 10.1 Feedback source의 역할

세 feedback source의 역할은 다음처럼 둔다.

```text
Oracle:
GT hidden state와 goal heuristic을 알고 항상 정답을 주는 source.
System upper bound를 확인한다.

Human-Proxy:
Oracle assumption을 낮춘 source.
Oracle 결과의 human feedback setting 연결 가능성을 점검한다.

Human:
실제 사람이 같은 planner query에 답하는 source.
Task performance claim을 확인한다.
```

이 구조에서 Human-Proxy는 Oracle과 Human 사이의 evaluation bridge이다. Human-Proxy의 성능 자체를 논문 contribution으로 두지 않고, Oracle 실험의 의미를 해석하는 데 사용한다.

### 10.2 Human response data의 위치

Human response data는 Human-Proxy를 만드는 목적 자체가 아니다. 역할은 calibration과 sanity check에 가깝다.

확인할 것:

1. 사람이 planner query를 이해할 수 있는가
2. 사람이 query 대상 object / state / predicate를 식별할 수 있는가
3. 질문 유형에 따라 정답률이 크게 달라지는가
4. visual ambiguity가 응답 정확도에 영향을 주는가
5. 사람이 주는 답이 belief update에 들어갈 수 있는 형태인가

이 데이터를 통해 Human-Proxy에 넣을 수 있는 것은 제한적인 response condition이다.

```text
P(answer | GT, question type, object/state visibility, predicate type, ambiguity)
```

이 수식의 의미는 Human-Proxy를 human model로 주장한다는 뜻이 아니다. Oracle의 완전한 정답 응답을 낮춘 feedback source를 만들 때 어떤 조건을 고려할지 정리한 것이다.

### 10.3 관련 연구에서 볼 축

관련 연구를 찾을 때 중심 질문은 "사람 응답을 얼마나 잘 모델링했는가"가 아니다. 봐야 할 것은 feedback source를 실험 설계 안에서 어떤 역할로 정의했는가이다.

1. Oracle / expert feedback 사용 연구
   1. feedback source를 완전한 expert로 두는지 확인한다.
   2. expert feedback을 upper bound로 해석하는지 확인한다.
   3. 실제 human feedback claim과 어떻게 연결하는지 확인한다.

2. Simulated user / proxy user 사용 연구
   1. 실제 사람 실험 전에 proxy user를 사용하는지 확인한다.
   2. proxy user가 pre-test, robustness check, bridge 중 어떤 역할인지 확인한다.
   3. proxy 결과를 논문 주장에 어떻게 사용했는지 확인한다.

3. Noisy / uncertain human feedback 연구
   1. feedback source가 항상 맞는다고 두지 않는 이유를 확인한다.
   2. noise, uncertainty, stochasticity를 system robustness 평가에 어떻게 쓰는지 확인한다.
   3. 우리 실험에서는 answer accuracy와 question-type dependent error로 옮겨볼 수 있다.

4. Preference-based RL / learning from human preferences
   1. 사람 선택을 확률적 feedback으로 해석하는 방식을 확인한다.
   2. Bradley-Terry 같은 noisy preference model의 역할을 확인한다.
   3. 우리 문제의 feedback은 predicate query answer라는 점을 명확히 둔다.

5. Human preference as planning constraint
   1. 사람 응답이 planning cost, constraint, preference로 들어가는 방식을 확인한다.
   2. feedback source의 신뢰도와 planning 반영 방식이 함께 정의되는지 확인한다.
   3. 우리 방법에서는 query answer가 belief / knowledge update와 replanning에 들어간다.

4. Ours가 All보다 적은 질문으로 성공률을 유지하는지 확인한다.
5. Ours가 No / Random보다 안정적인지 확인한다.

### 15.2 How 실험

논문에서 중요한 비교다.

해야 할 것:

1. Ours의 state-level query 결과를 정리한다.
2. KnowNo / Conformal Prediction 결과와 비교한다.
3. action-level 또는 option-level query와 state-level predicate query의 차이를 명확히 보여준다.
4. success rate, query count, workload/user burden 가능성을 본다.

### 15.3 What 실험

query content selection을 보여주는 실험이다.

해야 할 것:

1. Active Search baseline을 실제로 구현한다.
2. query/search 후보를 어떻게 만들지 정한다.
3. search space 증가, search time, query count를 기록한다.
4. random predicate / heuristic predicate / frontier entropy 기반 선택을 비교할 수 있는지 본다.

### 15.4 Answer accuracy 실험

보조 robustness 실험이다.

해야 할 것:

1. oracle vs noisy-oracle을 먼저 비교한다.
2. noisy-oracle error rate를 어떻게 둘지 정한다.
3. human-proxy는 tomato / wastesorting에서 조건부 noise를 구체화한다.
4. human-proxy는 main result보다 appendix/internal analysis로 둔다.

### 15.5 KnowNo 연결

현재 KnowNo baseline은 별도로 존재한다.

해야 할 것:

1. 현재 KnowNo 로그와 ours 로그 metric을 맞춘다.
2. KnowNo auto-answer에 `answer_type`을 넣을지 결정한다.
3. baseline comparison에서는 우선 oracle answer로 고정한다.

### 15.6 User study

PPT 기준으로 user study를 다시 설계해야 한다.

```text
N >= 30

```

1. task success rate
2. operation time
3. response time
