# 2026-07-09 Human-Proxy Noise TODO

## 1. 오늘 목표

`human-proxy`를 tomato, wastesorting 도메인에 대해 제대로 구현한다.

기본 원칙은 다음과 같다.

```text
human-proxy = oracle answer + selected situation noise
```

즉, `human-proxy`는 대부분의 경우 `_answer_oracle(...)`의 정답을 그대로 사용한다.
다만 특정 상황에서는 사람이 헷갈리거나 perception 결과를 잘못 신뢰하는 것처럼
일부러 noise를 섞는다.

noise를 넣을 상황은 나중에 직접 고른다.

## 2. 모드 역할 정리

현재 answer mode는 다음처럼 구분한다.

```text
oracle:
  항상 domain true state / oracle rule 기준으로 답한다.

noisy-oracle:
  oracle 답을 구한 뒤, 전역 error rate에 따라 무작위로 반대로 답한다.

human-proxy:
  oracle 답을 기본으로 쓰되, 사람이 헷갈릴 만한 특정 상황에만 noise를 넣는다.

human:
  실제 사용자 입력 또는 FeedbackManager의 human path에서 처리한다.
```

중요한 차이는 `noisy-oracle`과 `human-proxy`다.

`noisy-oracle`은 질문 내용과 상황을 보지 않고 일정 확률로 틀린다.
반면 `human-proxy`는 특정 predicate, action, object 상태, occlusion 같은 조건을 보고
그 상황에서만 틀릴 수 있다.

## 3. 구현 방향

### 3.1 기존 oracle 로직 재사용

`human-proxy`는 oracle 로직을 복사해서 따로 유지하지 않는다.
먼저 oracle 답을 계산한다.

```python
oracle_answer = _answer_oracle(
    target_fact,
    action,
    true_init_facts,
    current_facts,
)
```

그 다음 noise 적용 대상인지 확인한다.

```python
if _should_apply_human_proxy_noise(...):
    return _maybe_flip_answer(oracle_answer, error_rate)

return oracle_answer
```

이렇게 하면 oracle과 human-proxy의 기본 정답 기준이 어긋나지 않는다.

### 3.2 Noise 조건을 함수로 분리

도메인마다 noise 조건은 다르다.
따라서 다음 구조를 사용한다.

```python
def _answer_human_proxy(...):
    oracle_answer = _answer_oracle(...)
    if _should_apply_human_proxy_noise(...):
        return _flip_with_probability(oracle_answer, HUMAN_PROXY_ERROR_RATE)
    return oracle_answer
```

도메인별 조건 함수:

```python
def _should_apply_human_proxy_noise(...):
    ...
```

공통 flip 함수:

```python
def _flip_with_probability(answer: bool, error_rate: float) -> bool:
    if random.random() < error_rate:
        return not answer
    return answer
```

## 11. Transition / Observation 계산 Shape

belief update에서 사용하는 shape는 다음과 같다.

```python
outcomes = _get_transition_outcomes(belief.knowledge, action)
```

`outcomes`는 `NextStateOutcome` list다.

```text
outcomes length = N
```

각 outcome마다 다음 값을 만든다.

```python
frontiers.append(next_state)
tran_row.append(trans_prob)
obs_likelihood = observation_model.likelihood(obs, next_state, action)
obs_row.append(obs_likelihood)
```

따라서 shape는 다음과 같다.

```text
frontiers:          length N
transition_matrix: length N
observation_matrix:length N
```

계산은 element-wise 곱이다.

```python
unnormalized = transition_matrix * observation_matrix
weights = normalize(unnormalized)
```

의미:

```text
weight_i ∝ P(s'_i | s, a) * P(o | s'_i, a)
```

confidence observation의 경우 `P(o | s'_i, a)`는 다음처럼 해석한다.

```text
state가 observed fact를 만족하면:
  likelihood *= confidence

state가 observed fact를 만족하지 않으면:
  likelihood *= 1 - confidence
```

그래서 높은 confidence observation은 belief를 강하게 밀고, 낮은 confidence
observation은 belief를 약하게만 움직인다.

## 12. Duplicate Next State 제거

원칙적으로 `get_next_state_distribution()`은 실제 가능한 `next_state` 분포를
반환해야 한다.

따라서 서로 다른 transition outcome이 같은 `next_state`로 수렴하면, 그건
next-state distribution 관점에서는 중복이므로 제거해야 한다.

가능한 원인:

```text
1. add_facts가 이미 현재 state에 있음
2. del_facts가 현재 state에 없음
3. 서로 다른 add/del outcome이 적용 후 같은 fact set이 됨
4. domain trans.py에서 add/del 기준으로는 merge했지만 next_state 기준 merge는 안 됨
```

현재는 `transition.py`의 `get_next_state_distribution()`에서 중복 next state를
`state.facts + state.fluents` key 기준으로 merge한다.

merge 방식:

```text
같은 next_state를 만드는 outcome들:
  next_state는 하나만 유지
  probability는 모두 합산
```

출력 정보:

```text
action name
total next-state outcomes
unique next-state count
duplicate group count
duplicate group별 count / probability sum / facts preview
```

즉 로그는 디버깅용이고, 반환되는 `NextStateOutcome` list는 이미 unique
next_state distribution이다.

## 13. Observation Likelihood 해석

실제 로봇을 쓰더라도 sensor가 직접 belief를 업데이트해주는 것은 아니다.
센서는 observation과 confidence를 줄 뿐이고, 그 값을 어떻게 likelihood로 해석할지는
내부 belief update 알고리즘의 역할이다.

현재 구현에서는 symbolic observation fact를 Bernoulli random variable처럼 보고,
confidence를 Bernoulli likelihood로 사용한다.

즉 observation이 다음과 같을 때:

```text
observed(tomato3): confidence=0.65
unripe(tomato3): confidence=0.65
observed(tomato4): confidence=0.94
unripe(tomato4): confidence=0.94
```

candidate state `s`에 대해 다음처럼 계산한다.

```text
if s has fact:
  P(observed fact | s) = confidence

if s does not have fact:
  P(observed fact | s) = 1 - confidence
```

전체 observation likelihood는 각 observed fact가 독립이라는 가정하에 곱한다.

```text
P(o | s, a) ≈ Π_i P(o_i | s, a)
```

따라서 현재 likelihood 모델은 다음과 같이 정리한다.

```text
symbolic fact observation:
  independent Bernoulli likelihood approximation

confidence:
  해당 observed fact가 true일 sensor-side probability처럼 해석

belief update:
  transition probability와 observation likelihood를 곱한 뒤 normalize
```

이 방식은 근사다.
특히 `observed(tomato3)`와 `unripe(tomato3)`처럼 같은 detector output에서 나온
fact들은 실제로 독립이 아니다.

하지만 이 한계는 받아들인다.

이유:

```text
1. text simulator에서 실제 sensor posterior를 완전히 모델링할 수 없다.
2. YOLO confidence를 symbolic POMDP에 연결하기 위한 pragmatic approximation이다.
3. query threshold와 belief uncertainty를 실험하는 목적에는 충분하다.
4. 나중에 반드시 object-level joint likelihood로 바꿀 필요는 없다.
```

즉 현재 설계는 다음처럼 이해한다.

```text
실제 센서:
  observation + confidence를 생성

내부 알고리즘:
  confidence를 Bernoulli likelihood로 근사

남는 한계:
  fact 간 correlation은 무시
  일부 evidence double-counting 가능
```

이 한계는 모델의 오류가 아니라, 현재 실험 목적에 맞춘 의도적인 단순화다.

```text

```

Active Search 비교의 목적:

```text
query를 action으로 넣는 방식과 현재 방식의 차이를 보여준다.
```

효율 측면:

```text
query action을 action space에 넣으면 search space가 커진다.
POMCP는 매 planning step마다 action 후보를 탐색하므로,
물리 action과 query action이 같은 action set에 들어가면 branching factor가 증가한다.
```

디자인 철학 측면:

```text
query를 action으로 만들면 로봇이 "무엇을 질문할지"까지 자유롭게 선택한다.
현재 구조는 로봇이 action을 실행하고 observation/belief update 후,
uncertainty가 높을 때 feedback manager가 질문을 선택한다.
즉 사용자가 query policy를 control하는 구조다.
```

앞으로 비교할 축:

```text
ours:
  physical action planning과 query selection을 분리한다.

active-search baseline:
  query를 action space에 포함한다.
```

이 비교를 통해 보여주고 싶은 결론:

```text
query는 robot action이 아니라 interaction/refinement policy로 분리하는 편이 낫다.
```
