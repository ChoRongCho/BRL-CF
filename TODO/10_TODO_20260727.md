## 1. 최종 실험 구성

### E1. Threshold 실험 — When timing

목적:

```text
Ours의 질문 threshold가
질문 시점, task success와 query cost 사이에 만드는 trade-off를 분석한다.
```

조건:

```text
Method = Ours
What = Ours의 기본 fact selection
Feedback source = Oracle
변화 변수 = When threshold
```

핵심 지표:

- Task success rate
- Average query count / query rate
- Average execution steps
- Failure 또는 dead-end rate
- 필요할 경우 cumulative reward와 planning time

Threshold 후보 범위와 최종 operating point 선택 방식은 preliminary run 이후
확정한다. 메인 baseline과 ablation에서는 validation으로 선택한 동일 threshold를
사용한다.

### E2. Ablation 실험 — When / What

비교 조건:

| Method | When | What | 검증 목적 |
|---|---|---|---|
| `ours` | 제안 방식 | 제안 방식 | Full method |
| `ours-random-when` | Random | 제안 방식 | 질문 시점의 기여 |
| `ours-random-what` | 제안 방식 | Random | 질문 대상 선택의 기여 |

모든 조건은 Oracle feedback을 사용한다. Random 조건은 재현 가능한 random seed를
사용하고, 비교 시 질문 횟수 차이가 결과를 지배하지 않도록 random-when의 query
budget 또는 평균 query rate를 `ours`와 맞추는 방식을 우선 검토한다.

핵심 질문:

```text
When ablation:
  제안한 시점에 묻는 것이 무작위 시점에 묻는 것보다 효과적인가?

What ablation:
  task와 현재 불확실성에 맞는 fact를 고르는 것이
  무작위 fact를 묻는 것보다 효과적인가?
```

### E3. Baseline 실험

비교 조건:

| Method | Query 원리 | Feedback source |
|---|---|---|
| `ours` | 제안한 When / What | Oracle |
| `knowno` | Conformal uncertainty 기반 질의 | Oracle |
| `active-search` | Adapted Attr-POMDP의 joint task/query action search | Oracle |

공정한 비교를 위해 가능한 범위에서 다음을 공유한다.

```text
동일 domain / scene / task
동일 initial belief와 seed 집합
동일 task action 및 termination condition
동일 query 가능한 grounded fact
동일 Oracle answer
동일 feedback/query cost 정의
```

`active-search`는 `09_TODO`에서 논의한 **grounded-fact Adapted Attr-POMDP**로
확정한다. Yang et al. (ICRA 2022)의 joint task/query action planning 구조를 현재
symbolic domain에 적용하고, 원 논문의 attribute 질문을 grounded Boolean fact
질문으로 대체한 구현이다. 코드와 결과 경로에서는 canonical method 이름으로
`active-search`를 사용하고, 로그에는 `implementation=adapted_attr_pomdp`와 원 논문
및 adaptation 내용을 함께 기록한다.

### E4. Feedback source 실험

E1–E3는 모두 Oracle로 수행하여 algorithm 자체를 통제해서 비교한다. 실제
feedback source의 영향은 별도 실험으로 분리한다.

비교 조건:

| Method | Oracle | VLM | Human |
|---|---:|---:|---:|
| `ours` | E1–E3 결과 활용 또는 reference | 실행 | 실행 |
| `knowno` | E3 결과 활용 또는 reference | 실행 | 실행 |

즉, feedback source 실험의 실제 추가 조합은 다음 네 개다.

```text
ours-vlm
ours-human
knowno-vlm
knowno-human
```

VLM provider는 GPT 계열 vision model을 사용한다. 이 provider는 Ours 전용으로
만들지 않고, 동일한 observation/evidence와 질문 형식을 받아 `ours`와 `knowno`
모두에 연결할 수 있는 공통 answer interface로 만든다.

VLM과 Human 비교 시 task performance 외에 source 자체의 특성을 함께 기록한다.

- Answer accuracy 또는 Oracle agreement
- Invalid / unparseable answer rate
- Response latency
- Task success rate
- Average query count
- 질문당 또는 episode당 비용(VLM은 API cost, Human은 interaction burden)

## 2. `09_TODO`와의 연결 및 변경점

유지하는 원칙:

- E1–E3는 Oracle을 사용한 controlled algorithm evaluation이다.
- Main baseline은 전체 query architecture를 비교한다.
- Ablation은 Ours 내부의 When과 What 기여를 분리한다.
- Human과 VLM은 algorithm 비교에 섞지 않고 feedback source 축에서 다룬다.
- 질문 수뿐 아니라 success, execution cost와 query relevance를 함께 본다.

이번 문서에서 단순화하거나 변경한 점:

```text
09_TODO의 넓은 ablation 후보
→ ours / ours-random-when / ours-random-what의 3조건으로 축소

09_TODO의 main baseline
→ ours / knowno / active-search의 3조건으로 확정

09_TODO의 Human/VLM 논의
→ ours와 knowno 각각에 VLM과 Human을 연결하는 2×2 추가 실험으로 확정
```

`09_TODO`에서 설명한 symbolic action model, conflict-triggered feedback 및
interpretable grounded fact의 논문 framing은 유지한다. 다만 아래 query trigger
정의가 아직 확정되지 않았으므로 E1을 구현하기 전에 반드시 코드와 논문 용어를
일치시킨다.

```text
안 A: entropy/confidence threshold가 직접 When을 결정

안 B: transition–observation conflict가 query opportunity를 만들고,
      threshold가 실제 질문 여부 또는 timing을 결정
```

Threshold 실험을 `When timing` 실험으로 부르려면 threshold 값이 실제 실행
흐름에서 질문 시점을 어떻게 바꾸는지 명시적으로 로그에 남겨야 한다.

## 3. 구현 전 공통 실험 규약

### 3.1 공통 method 이름

결과 CSV, log directory와 figure label에서 다음 canonical name을 사용한다.

```text
ours
ours-random-when
ours-random-what
knowno
active-search
```

Feedback source는 method 이름과 분리된 field로 둔다.

```text
feedback_source ∈ {oracle, vlm, human}
```

### 3.2 공통 로그 필드

최소한 다음 정보를 method에 상관없이 같은 schema로 저장한다.

- Experiment group: `threshold / ablation / baseline / feedback-source`
- Domain, scene, task와 seed
- Method와 feedback source
- Threshold 및 method-specific parameter
- Task success와 termination reason
- Execution step 수와 cumulative reward
- Query 시점, query count와 질문한 grounded fact
- Feedback answer, parse 성공 여부와 latency
- 질문 전후 belief 또는 uncertainty 변화

### 3.3 공정성 원칙

- 동일 비교표 안에서는 동일 scene/seed를 paired run으로 사용한다.
- Hyperparameter는 test set이 아니라 validation run에서 고른다.
- Oracle은 모든 method에 동일한 ground-truth answer rule을 제공한다.
- VLM/Human 조건에서도 planner와 method parameter는 Oracle 실험에서 고정한 값을
  그대로 사용한다.
- Random ablation은 seed별 반복 결과와 평균/분산을 함께 보고한다.
