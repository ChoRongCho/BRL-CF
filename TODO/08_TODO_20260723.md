# 2026-07-23 실험 구조 및 논문 스토리

## 0. 이번 문서의 목적

현재 실험 후보는 크게 세 묶음이다.

1. Threshold에 따른 성능 변화
2. 제안 시스템 내부 ablation
3. 다른 system-initiative feedback 방법과의 비교

여기에 feedback source까지 `Oracle / Noisy-Oracle / Human / VLM`으로 모두
조합하면 실험 수만 많아지고, 각 결과가 전달하는 메시지는 반복될 가능성이 크다.

따라서 feedback source를 하나의 독립 실험 축으로 전부 교차시키지 않는다.
각 source에 서로 다른 역할을 부여하고, 논문의 핵심 알고리즘 비교는 통제된
Oracle 환경에서 수행한다.

## 1. 논문의 중심 스토리

### 1.1 문제

부분 관측 환경에서는 로봇이 현재 world state를 확실히 알지 못한다. 외부
피드백을 항상 요청하면 불확실성은 줄일 수 있지만 상호작용 비용이 커지고,
전혀 요청하지 않으면 잘못된 belief를 바탕으로 행동할 수 있다.

따라서 시스템은 다음 두 결정을 스스로 내려야 한다.

```text
When:
  현재 불확실성이 실제로 외부 확인을 요구할 만큼 큰가?

What:
  전체 state를 요청하지 않고 어떤 grounded fact 하나를 확인해야
  competing hypotheses를 가장 효과적으로 구분할 수 있는가?
```

### 1.2 제안 방법

```text
POMDP action execution
→ observation 및 belief update
→ normalized belief entropy로 질문 필요성 판단
→ expected posterior entropy로 grounded fact 선택
→ feedback을 belief와 knowledge base에 반영
→ replanning
```

질문은 POMDP의 action space 안에서 task action과 공동 최적화되지 않는다.
기존 planner 위에 결합되는 corrective feedback layer라는 점이 핵심이다.

### 1.3 실험이 만들어야 하는 논리

```text
E1. Threshold analysis:
    언제 물을지를 제어하는 entropy threshold가 어떤 trade-off를 만드는가?

E2. Component ablation:
    제안 시스템의 When과 What이 각각 실제로 필요한가?

E3. Algorithm comparison:
    다른 system-initiative feedback 방법과 비교해도 효율적인가?

E4. Human–VLM feedback study:
    Oracle에서 확인한 성능이 실제 feedback source에서도 어느 정도 유지되는가?
    사람이 답할 때와 VLM이 답할 때 task performance는 어떻게 달라지는가?
```

E1–E3는 Oracle을 이용한 controlled algorithm evaluation이다. 여기서 Oracle
결과는 완벽한 feedback이 주어졌을 때 각 방법이 달성할 수 있는 upper bound로
해석한다. E4에서는 동일한 Ours에 Human과 VLM을 연결하여 실제 feedback
source에서의 end-to-end 성능을 비교한다.

```text
Stage A — Oracle upper-bound evaluation:
  feedback 오류를 제거하고 When/What 및 baseline 자체를 비교

Stage B — Actual feedback-source evaluation:
  Ours의 answer provider만 Human과 VLM으로 교체
  → 실제 answer quality와 downstream task performance 비교
```

## 2. Feedback source를 분배하는 원칙

### 2.1 전체 조합을 실행하지 않는 이유

다음과 같은 완전요인 실험은 피한다.

```text
모든 method
× 모든 threshold
× 모든 domain
× Oracle / Noisy-Oracle / Human / VLM
```

문제점:

- 알고리즘 차이와 feedback source의 정확도 차이가 섞인다.
- Human과 VLM은 매 trial마다 응답 품질과 지연이 달라 공정한 baseline 비교가
  어렵다.
- 같은 결론을 여러 표에서 반복하게 된다.
- Human 대상 실험 수가 불필요하게 커진다.
- VLM 모델 및 prompt 성능 평가가 논문의 중심처럼 보일 수 있다.

### 2.2 Source별 역할

| Feedback source | 논문에서의 역할 | 적용할 실험 |
|---|---|---|
| Oracle | 완벽한 feedback에서의 알고리즘 성능 상한 | E1, E2, E3 |
| Human | 실제 사용자가 답할 때의 task/interaction 성능 | E4 user study |
| VLM | 동일 질문을 자동화된 visual source가 답할 때의 성능 | E4 user study |
| Noisy-Oracle | 선택적인 오류 민감도 분석 | 필요할 때만 Appendix |

핵심 원칙:

```text
Oracle:
  method 자체가 낼 수 있는 upper bound를 평가

Human:
  사람이 실제 질문에 답할 때 end-to-end 성능을 평가

VLM:
  동일 질문을 VLM이 답할 때 Human 및 Oracle과의 차이를 평가
```

Human과 VLM은 별개의 작은 demonstration으로 흩어놓지 않고 하나의 user-study
축에서 비교한다. Noisy-Oracle은 독립 실험 축에서 제거한다.

## 3. E1 — Threshold 분석

### 3.1 목적

Entropy threshold는 task success와 query cost 사이의 operating point를
결정한다. 이 실험의 목적은 domain별 최적 숫자를 찾는 것이 아니라 다음을
보이는 것이다.

```text
threshold가 낮음:
  불확실성을 더 허용
  → 질문 감소
  → 잘못된 행동 또는 실패 가능성 증가

threshold가 높음:
  작은 불확실성에도 확인
  → 질문 증가
  → 성공률 증가 후 포화
```

### 3.2 조건

고정:

```text
Method = Ours
What = expected-posterior-entropy fact selection
Feedback = Oracle
```

변화:

```text
τ ∈ {0.0, 0.1, ..., 1.0}
또는 preliminary run으로 의미 있는 범위를 좁힌 5~7개 지점
```

Domain:

- Waste sorting
- Tomato harvesting

### 3.3 Domain마다 적절한 threshold가 다를 때

Domain별 최적 threshold를 test result를 보고 각각 선택하면 과적합처럼 보인다.
다음 절차를 사용한다.

1. 두 domain의 validation seed에서 threshold sweep을 수행한다.
2. success와 query count의 Pareto curve를 그린다.
3. 두 domain 모두에서 안정적인 공통 plateau에 있는 `τ_global` 하나를 선택한다.
4. 이후 모든 메인 실험은 동일한 `τ_global`을 사용한다.
5. Domain별 최적 threshold는 supplementary analysis로만 보고한다.

공통 threshold가 정말 성립하지 않으면 다음처럼 정직하게 기술한다.

```text
The threshold is an operating parameter reflecting the acceptable
interaction-risk trade-off. Although the domains exhibit different
optimal points, a single validation-selected threshold remains within
the stable performance region of both domains.
```

중요한 것은 두 domain의 최적값이 완전히 같다는 주장이 아니다. normalized
entropy 덕분에 공통 threshold가 합리적인 범위에서 재사용 가능하고, 사용자가
원하는 query-cost/risk 수준에 맞춰 조정할 수 있음을 보이는 것이다.

### 3.4 지표와 그림

필수:

- Task success rate
- Average query count
- Query rate per execution step
- Failure/dead-end rate
- Average execution steps

선택:

- Final belief entropy
- Planning time
- Composite utility `success - λ × query_cost`

메인 그림:

```text
x축: threshold
왼쪽 y축: success rate
오른쪽 y축: average query count
domain별 subplot
```

추가로 `success rate–query count` Pareto plot을 제시하면 threshold의 의미가
더 명확해진다.

## 4. E2 — 자체 시스템 Ablation

### 4.1 비교 조건

| Method | When | What | 확인하는 것 |
|---|---|---|---|
| All | 모든 query opportunity | Ours | 항상 묻기의 성능과 상호작용 상한 |
| No | 묻지 않음 | 없음 | feedback 없는 하한 |
| Ours | Entropy trigger | Expected-entropy fact | 완성된 시스템 |
| Random-When | Random trigger | Ours | When 설계의 효과 |
| Random-What | Ours | Random candidate fact | What 설계의 효과 |

`All`은 매 simulation step마다 무조건 묻는 것으로 정의하지 않는다. 질문할
candidate fact가 존재하는 query opportunity마다 묻는 것으로 정의한다. 그렇지
않으면 의미 없는 질문을 대량 생성하는 인위적인 약한 baseline이 된다.

### 4.2 공정한 Random-When 정의

Random-When이 Ours보다 단순히 질문을 적게 또는 많이 해서 차이가 나면 When
ablation이 아니다.

권장 정의:

```text
Ours가 validation set에서 보인 평균 query rate를 p로 계산
각 query opportunity에서 probability p로 질문
```

또는 seed별 동일 query budget을 부여한다. 메인 결과에는 query-matched
Random-When을 사용한다.

### 4.3 공정한 Random-What 정의

Random-What은 Ours와 동일한 시점에 질문하고, 동일 candidate set에서 fact만
무작위로 선택한다.

```text
When = Ours trigger
Candidate facts = Ours와 동일
What = uniform random
```

이렇게 해야 candidate generation이 아니라 information-based selection의
효과만 분리할 수 있다.

### 4.4 Feedback source

E2는 모두 Oracle로 수행한다.

이유:

- When/What component의 효과만 분리할 수 있다.
- 동일 질문에는 항상 동일한 정답이 돌아온다.
- Human 또는 VLM 정확도 차이가 ablation 결과에 섞이지 않는다.

### 4.5 핵심 해석

예상되는 논리:

```text
No:
  질문 비용은 없지만 불확실성으로 인해 성공률이 낮음

All:
  성공률은 높지만 불필요한 질문이 많음

Random-When:
  같은 수준의 query budget에서도 필요한 순간을 놓침

Random-What:
  필요한 순간에 질문해도 정보량이 낮은 fact를 고르면 비효율적임

Ours:
  All에 가까운 성공률을 더 적은 질문으로 달성
```

반드시 Ours가 모든 단일 지표에서 1등이어야 하는 것은 아니다. 핵심은
`success–query cost`의 Pareto trade-off다.

## 5. E3 — 다른 System-Initiative Feedback 방법과 비교

### 5.1 비교 대상

| Method | 질문 결정 구조 | 대표 비교 의미 |
|---|---|---|
| Ours | Planner 외부 entropy trigger + fact selection | 제안 architecture |
| Active Search 계열 | Information acquisition을 planning objective/action에 포함 | Joint information planning |
| KnowNo | Conformal uncertainty 기반 action-level assistance | Action choice query |

### 5.2 비교 질문

이 비교는 “어느 solver가 더 좋은가?”가 아니라 다음 system design question에
답해야 한다.

```text
정보 획득을 task planning 안에서 공동 최적화하지 않고도,
분리된 corrective query layer가 task success와 query efficiency를
유지하면서 계산 및 적용 복잡도를 줄일 수 있는가?

전체 state 또는 다음 action을 요청하지 않고,
grounded fact verification만으로 ambiguity를 해소할 수 있는가?
```

### 5.3 Feedback source

메인 비교는 Oracle로 통일한다.

- Ours의 fact query에는 queried fact의 truth value를 반환한다.
- Active Search의 ask action에는 해당 observation/query model의 정답을 반환한다.
- KnowNo에는 correct action option 또는 help response를 반환한다.

질문의 단위가 서로 다르기 때문에 raw query count만 비교하면 불공정할 수 있다.
다음을 함께 보고한다.

- Task success
- Number of interruptions
- Information amount per response
- Total feedback payload
- Execution steps
- Planning wall-clock time
- Timeout rate
- Grounded action/search-space size

가능하면 feedback payload를 다음처럼 별도로 정의한다.

```text
Binary fact answer:
  약 1 bit 또는 yes/no 1회

Action selection:
  log2(number of presented actions) 수준

Full-state information:
  전달된 predicate 수 또는 state description length
```

정확한 정보량 환산이 논쟁적이면, `interruptions`, `facts supplied`,
`options presented`를 각각 원자료로 보고하고 하나의 숫자로 억지로 합치지 않는다.

### 5.4 Budget-matched 비교

방법별 query frequency가 크게 다르면 다음 두 결과를 모두 제시한다.

1. 각 방법의 기본 설정 결과
2. 동일 feedback budget 또는 동일 success target에서의 결과

이를 통해 reward/query-cost tuning 차이로 인한 승패를 줄인다.

### 5.5 논문에서의 위치

E3는 main baseline table로 둔다. 다만 Active Search 구현이 논문의 query
semantics와 지나치게 다르면 동일한 방법인 것처럼 포장하지 않고
`alternative information-acquisition architecture`로 명확히 표현한다.

## 6. E4 — Human–VLM Feedback User Study

### 6.1 목적

E1–E3가 “완벽한 답이 주어졌을 때 어느 알고리즘이 좋은가?”를 검증했다면,
E4는 다음 실제 적용 질문에 답한다.

```text
Ours가 생성한 동일한 grounded-fact query에 대해
사람이 답하는 경우와 VLM이 답하는 경우,
answer quality와 downstream task performance는 어떻게 달라지는가?
```

여기서 Human과 VLM은 알고리즘 baseline이 아니라 **동일한 Ours에 연결되는
feedback provider 조건**이다.

### 6.2 비교 조건

핵심 조건:

| Condition | Query policy | Feedback provider |
|---|---|---|
| Oracle-Ours | Ours | Ground-truth oracle |
| Human-Ours | Ours | Participant |
| VLM-Ours | Ours | Fixed VLM and prompt |

Oracle-Ours는 E1–E3에서 얻은 upper bound reference다. User study의 실제 비교
대상은 Human-Ours와 VLM-Ours이며, 동일 scene과 query를 가능한 한 paired하게
구성한다.

```text
동일 domain / scene / seed
동일 Ours threshold
동일 candidate facts와 query wording
동일 success criterion과 maximum step
feedback provider만 교체
```

### 6.3 참가자와 실험 설계

참가자는 5~6명으로 작은 규모의 exploratory user study를 수행한다.

권장 방식:

```text
Within-subject:
  모든 참가자가 동일한 대표 scenario들을 수행

Human condition:
  참가자가 질문에 직접 답함

VLM condition:
  동일 scene 이미지와 동일 fact query에 VLM이 답함
  참가자는 VLM을 조작하는 것이 아니라 비교용 결과를 제공
```

Human과 VLM을 공정하게 비교하려면 가능한 경우 각 query event의 scene snapshot과
질문을 저장한 뒤, 동일 입력을 두 provider에게 제시한다. 이렇게 하면 planner가
이전 오답 때문에 서로 다른 trajectory로 갈라지는 문제와 개별 answer quality를
분리해 볼 수 있다.

따라서 분석을 두 층으로 나눈다.

```text
Query-level paired comparison:
  동일 snapshot/query에 대한 Human과 VLM의 답 비교

Episode-level end-to-end comparison:
  각 provider의 답을 실제 belief update에 반영했을 때 task 결과 비교
```

### 6.4 평가 지표

#### Query-level

- Answer accuracy against ground truth
- Precision/recall 또는 predicate별 accuracy
- Unknown/no-answer rate
- Response latency
- Human–VLM agreement

#### Episode-level

- Task success rate
- Average query count
- Failure/dead-end rate
- Execution steps
- Oracle upper bound 대비 success gap
- 잘못된 답 이후 correct hypothesis가 제거된 횟수

#### Human에만 적용

- 질문 이해도
- 응답 확신도
- 주관적 부담
- 이해하지 못한 predicate/query 사례

Human 전용 설문 지표를 VLM과 억지로 비교하지 않는다. Human–VLM 비교의 공통
지표는 answer accuracy, latency, unknown rate, task success로 제한한다.

### 6.5 해석

가능한 결과와 포장:

```text
Human ≈ Oracle, Human > VLM:
  현재 system은 human corrective feedback에 가장 적합하고,
  VLM integration은 가능하지만 perception reliability가 병목

Human ≈ VLM < Oracle:
  provider-independent loop는 작동하지만 imperfect answer가 공통 병목

VLM ≈ Human ≈ Oracle:
  VLM이 human feedback을 자동화할 가능성을 보여주는 강한 system 결과

VLM > Human:
  제한된 visual predicate에서는 VLM 자동 응답이 유효하지만,
  작은 참가자 수 때문에 일반적인 human superiority 비교로 확대하지 않음
```

5~6명으로 Human과 VLM의 일반적인 우열을 주장하지 않는다. 이 실험의 주장은
다음 수준으로 제한한다.

```text
The same corrective query loop was evaluated with human and VLM
feedback providers, showing how provider answer quality translates
into downstream task performance.
```

### 6.6 실행 범위

- Ours만 Human/VLM 조건으로 실행한다.
- All/No/Random 및 외부 baseline을 user study에서 반복하지 않는다.
- VLM 모델은 하나로 고정하고 model benchmark를 하지 않는다.
- 가능하면 두 domain을 사용하되, user burden이 크면 대표 task를 domain별
  소수 scenario로 제한한다.
- Human/VLM 비교 전에 질문 문장과 scene visualization을 internal pilot으로
  검증한다.

## 7. Appendix Optional — Noisy-Oracle Sensitivity

Noisy-Oracle은 메인 research question과 필수 실험에서 제거한다.

다음 상황에서만 appendix에 추가한다.

- Reviewer가 imperfect feedback에 대한 통제 분석을 요구할 가능성이 큼
- Human/VLM 결과와 Oracle upper bound 사이에 큰 차이가 발생함
- 그 차이가 answer error 때문이라는 설명을 보강할 필요가 있음
- 구현 비용이 매우 낮고 main experiment 일정에 영향을 주지 않음

추가한다면 Ours에 대해서만 최소한으로 수행한다.

```text
Answer error ε ∈ {0.0, 0.1, 0.2}
Unknown rate μ ∈ {0.0, 0.1}
```

이는 새로운 feedback source의 demonstration이 아니라, Human/VLM에서 관찰된
오답이 task performance에 미치는 영향을 해석하기 위한 supplementary sensitivity
analysis로만 기술한다.

## 13. 결과에 따른 판단 기준

### Threshold가 domain마다 크게 다를 경우

- Domain-specific optimality를 주장하지 않는다.
- Global threshold의 성능 손실을 보고한다.
- Threshold를 deployer가 조절하는 interaction-risk parameter로 정의한다.
- 필요하면 domain calibration을 limitation으로 둔다.

### Ours가 All보다 성공률이 낮을 경우

질문 수가 충분히 크게 감소하고 success 손실이 작다면 Pareto trade-off로 설명할
수 있다. 둘 다 나쁘다면 trigger 설계를 수정해야 한다.

### Random-When과 차이가 없을 경우

현재 entropy가 failure-relevant uncertainty를 제대로 측정하는지 확인한다.
단순 normalized entropy 대신 action-relevant 또는 goal-relevant uncertainty가
필요할 수 있다.

### Random-What과 차이가 없을 경우

Candidate set이 너무 작거나 모든 fact의 정보량이 비슷한지 확인한다. 이 경우
What contribution을 강하게 주장하기 어렵고, 더 모호한 scene 또는
goal/precondition relevance가 필요하다.

### VLM 결과가 낮을 경우

시스템 알고리즘 실패와 VLM perception 실패를 분리한다. Oracle 메인 결과가
유지된다면 VLM은 negative case study와 limitation으로 남길 수 있다.

### Human 표본이 부족할 경우

5~6명 결과로 Human과 VLM의 일반적 우열을 주장하지 않는다. 동일 query에서
관찰된 accuracy, latency, failure 유형과 downstream task 결과를 exploratory
evidence로 보고한다.

## 14. 최종 권장 결론

실험의 중심은 다음 세 문장으로 수렴해야 한다.

```text
1. Ours determines when to request feedback by exposing a controllable
   interaction–risk trade-off through normalized belief entropy.

2. Ours determines what to request by selecting a grounded fact that
   maximally reduces ambiguity, achieving higher query efficiency than
   random timing or random content.

3. The corrective query layer remains separate from task-action planning,
   compares favorably with alternative system-initiative architectures,
   and uses the same core decision mechanism with human and VLM feedback
   providers; the controlled oracle results serve as an upper bound.
```

세 번째 문장의 핵심은 Oracle, Human, VLM을 동등한 세 baseline으로 보는 것이
아니다. **Oracle은 알고리즘의 upper bound를 만들고, Human과 VLM은 동일한
제안 시스템에 연결되는 실제 feedback-provider 조건으로 비교한다**는 것이다.
Noisy-Oracle은 이 스토리에 필수적이지 않으며, 실제 결과를 해석할 필요가 있을
때만 appendix에 추가한다.

### 15.1 실험

본 실험은 제안 시스템을 네 가지 관점에서 평가한다. 첫째, 정규화된 belief
entropy의 임계값에 따라 작업 위험과 상호작용 비용 사이의 절충 관계가 어떻게
변하는지 분석한다. 둘째, 질문 시점(\textit{When})과 질문 내용(\textit{What})을
각각 제거하거나 무작위화하여 두 구성 요소의 기여도를 검증한다. 셋째, 제안
방법을 다른 system-initiative feedback 방법과 비교하여 작업 성공률, 피드백
효율성 및 계산 비용을 평가한다. 넷째, 동일한 제안 방법에 Human과 VLM을 각각
feedback provider로 연결하여 실제 응답 품질이 downstream 작업 성능에 미치는
영향을 분석한다.

앞의 세 실험에서는 feedback 오류로 인한 영향을 제거하고 각 알고리즘의 성능을
통제된 조건에서 비교하기 위해 ground-truth Oracle을 사용한다. 따라서 이
결과는 완전한 피드백이 제공될 때 각 방법이 달성할 수 있는 성능 상한으로
해석한다. Human--VLM 실험에서는 query policy와 질문 문장을 동일하게 유지하고
feedback provider만 변경한다.

#### 15.1.1 실험 환경

제안 방법은 waste sorting과 tomato harvesting의 두 작업에서 평가하였다.
Waste sorting 환경에서 로봇은 총 `[00]`개의 물체를 general, paper, can 및
plastic의 네 범주로 분류한다. 각 물체의 범주는 초기에 알려지지 않으며,
가림과 관측 오류로 인해 하나의 관측만으로는 범주를 확정하지 못할 수 있다.
로봇은 detect, pick 및 place를 수행하며, 모든 물체를 올바른 수거함에 배치하면
episode가 성공한 것으로 판정한다.

Tomato harvesting 환경에서 로봇은 총 `[00]`개의 토마토를 대상으로 navigation,
detect, pick, scan, place 및 discard를 수행한다. 각 토마토는 ripe, unripe
또는 rotten 상태를 가지며, 상태와 위치는 초기에 알려지지 않는다. 모든 ripe
토마토를 수확하고 모든 rotten 토마토를 폐기하되 unripe 토마토를 훼손하지
않으면 episode가 성공한 것으로 판정한다.

각 domain-condition 조합은 `[00]`개의 scenario와 scenario당 `[00]`개의
무작위 episode로 구성하여 총 `[000]`회 반복하였다. 모든 방법에는 동일한
초기 상태와 pseudorandom seed를 사용하였다. 각 episode의 최대 실행 step은
`[00]`으로 제한하였으며, 제한 안에 목표를 완료하지 못하거나 복구할 수 없는
상태에 도달한 경우 실패로 기록하였다. Planner의 discount factor는
`[0.00]`, UCB exploration constant는 `[0.00]`, 최대 simulation depth는
`[00]`, planning step당 Monte Carlo simulation 횟수는 `[000]`으로 설정하였다.

주요 지표는 task success rate, episode당 평균 query 수, 실행 step당 query
rate, failure/dead-end rate 및 성공 episode의 평균 실행 step이다. 외부
baseline 비교에서는 planning wall-clock time, timeout rate, feedback
interruption 수와 feedback payload를 추가로 측정하였다. Query rate는 전체
실행 step 가운데 하나 이상의 질문이 발생한 step의 비율로 정의하였다.
Feedback payload는 binary fact의 경우 제공된 fact 수, action query의 경우
제시된 선택지 수로 각각 보고하였다.

#### 15.1.3 구성 요소 Ablation

질문 시점과 질문 내용의 독립적인 기여도를 확인하기 위해 All, No, Ours,
Random-When 및 Random-What을 비교하였다. All은 candidate fact가 존재하는
모든 query opportunity에서 질문하고, No는 피드백 없이 작업을 수행한다.
Random-When은 validation set에서 Ours가 사용한 평균 query rate
$p=[0.00]$에 맞추어 각 query opportunity에서 무작위로 질문한다.
Random-What은 Ours와 정확히 같은 시점에 질문하지만 동일 candidate set에서
fact 하나를 균일하게 무작위 선택한다. 모든 조건에는 Oracle이 답하였으며,
동일한 episode seed를 사용하였다.

### 15.2 종합 Discussion

실험 결과는 부분 관측 환경에서 system-initiative feedback을 설계할 때
질문의 시점과 내용이 모두 중요하다는 것을 보여준다. 임계값 실험에서 낮은
$\tau$는 중요한 불확실성을 해결하지 못해 task failure를 증가시켰고, 지나치게
높은 $\tau$는 성공률의 추가 향상 없이 query 수만 증가시켰다. 즉, 피드백의
가치는 질문 횟수 자체가 아니라 현재의 불확실성이 미래 행동과 목표 달성에
미치는 영향에 의해 결정된다. 두 domain의 validation 결과로 선택한 하나의
공통 임계값이 안정적인 성능 구간에 포함되었다는 점은 normalized belief
entropy가 서로 다른 symbolic state 규모에서도 일관된 operating parameter로
사용될 수 있음을 시사한다.

구성 요소 ablation은 \textit{When}과 \textit{What}의 역할을 분리하여
보여준다. Query budget을 일치시킨 Random-When보다 Ours의 성공률이 높았다는
결과는 entropy trigger가 단순한 무작위 interruption보다 failure-relevant
uncertainty를 더 잘 포착했음을 의미한다. 동일한 시점과 candidate set을 사용한
Random-What보다 Ours가 높은 성공률과 낮은 fact cost를 보인 결과는 expected
posterior entropy가 competing hypothesis를 구분하는 질문을 선택했음을
보여준다. All은 가장 적극적인 감독으로 높은 성공률을 달성했지만, Ours는 그와
유사한 성공률을 훨씬 적은 질문으로 달성하였다. 따라서 제안 방법의 핵심 이점은
모든 단일 지표에서 절대적인 최댓값을 얻는 것이 아니라 success--interaction
cost의 Pareto frontier를 개선하는 데 있다.

외부 방법과의 비교는 corrective feedback layer를 task-action planning과
분리한 architecture의 장점을 보여준다. Active Search처럼 정보 획득을 전체
planning objective에 포함하면 task action과 information action을 함께
탐색할 수 있지만, 상태와 물체 수가 증가할수록 search space와 planning
time이 커진다. Ours는 기존 POMDP planner의 action space를 변경하지 않고
belief update 이후에만 질문 여부와 fact를 결정하여 더 낮은 계산 비용으로
높은 성공률을 유지하였다. KnowNo의 action-level query는 다음 행동을 직접
선택하는 데 유용하지만, 행동을 모호하게 만든 state uncertainty를 지속적으로
해소하지는 못하였다. Grounded fact를 knowledge base에 반영하는 Ours의
응답은 이후 여러 planning step에서 재사용되므로 더 높은 feedback 효율성을
보였다.

Human--VLM 실험은 Oracle 결과가 실제 provider에서 어떻게 변화하는지를
보여준다. Human-Ours가 Oracle 성능에 근접한 결과는 제안한 질문 단위가 실제
사용자에게 이해 가능하고, 사람이 continuous supervisor가 아니라 targeted
verifier로 참여할 수 있음을 시사한다. VLM-Ours는 Human-Ours보다 낮은 성능을
보였으나 No 조건보다 높은 성공률을 유지하여 자동 feedback provider로서의
가능성을 보였다. 중요한 점은 Human, VLM 및 Oracle을 서로 다른 query
algorithm으로 비교한 것이 아니라, 동일한 Ours의 질문에 연결되는 provider로
비교했다는 것이다. 따라서 Human과 VLM 사이의 downstream 성능 차이는 query
policy의 차이가 아니라 응답 정확도와 오류 유형의 차이로 해석할 수 있다.

두 domain의 결과 차이도 작업 구조와 일치한다. Waste sorting에서는 하나의
범주 fact를 확인하면 해당 물체의 후속 pick-and-place 결정이 직접 확정되므로
적은 질문으로도 높은 성능을 얻었다. Tomato harvesting에서는 위치, 성숙도,
scan 결과 및 grasp 상태에 관한 불확실성이 긴 행동 순서에 걸쳐 누적되므로 더
많은 질문과 긴 실행 경로가 필요하였다. 그럼에도 두 domain에 동일한
query-triggering 및 fact-selection mechanism을 적용하고 domain-specific
predicate, skill 및 observation model만 교체했다는 점은 제안 구조의 적용
가능성을 뒷받침한다.

### 15.3 한계

본 연구에는 다음과 같은 한계가 있다. 첫째, Oracle 기반 결과는 완전한 응답을
가정한 알고리즘 성능의 상한이며, 실제 환경의 perception error와 사용자
오류를 모두 반영하지 않는다. Human--VLM 실험을 통해 이 차이를 일부
분석했지만 참가자 수가 `[00]`명이고 scenario 수가 `[00]`개로 제한적이므로,
Human과 VLM의 일반적인 우열이나 광범위한 human-factors 결론으로 확대해서는
안 된다.

둘째, belief frontier의 weight와 observation likelihood는 domain model의
확률값에 의존한다. 본 실험에서는 query policy 자체의 효과를 분리하기 위해
고정된 확률을 사용했으나, 확률이 잘못 calibration되면 entropy와 query
시점이 함께 달라질 수 있다. 향후에는 transition 및 observation probability의
misspecification에 대한 민감도 분석과 online calibration이 필요하다.

셋째, 제안 방법은 candidate fact가 task-relevant predicate로 구성되어 있다는
가정에 의존한다. Candidate set에 필요한 fact가 포함되지 않거나, 모든
candidate의 정보량이 유사하면 expected posterior entropy의 이점이 감소할 수
있다. 더 큰 open-world 환경에서는 candidate generation, natural-language
grounding 및 새 predicate의 동적 추가가 필요하다.

넷째, 현재 방법은 provider의 답을 즉시 belief와 knowledge base에 반영한다.
Human과 VLM의 오답이 ground-truth hypothesis를 제거한 사례에서 확인했듯이,
불완전한 feedback을 다루려면 응답 신뢰도, 재질문, 복수 source의 합의 및
모순 복구를 명시적으로 모델링해야 한다. 이는 appendix의 Noisy-Oracle
sensitivity와 향후 실제 robot 장기 실험에서 추가로 검증할 수 있다.

### 15.4 실험 결론

종합하면, 제안 방법은 normalized belief entropy를 이용해 피드백이 필요한
시점을 결정하고 expected posterior entropy를 이용해 ambiguity를 가장 크게
줄이는 grounded fact를 선택하였다. 그 결과 All과 유사한 task success를 더
적은 질문으로 달성했으며, random timing, random content 및 외부
system-initiative feedback 방법보다 우수한 success--interaction trade-off를
보였다. 또한 planner의 task-action space를 변경하지 않는 corrective layer로
구현되어 joint information planning보다 낮은 계산 비용을 유지하였다.
마지막으로 동일한 query loop를 Human과 VLM provider에 연결했을 때도
end-to-end 작업 성능이 유지되어, Oracle에서 확인한 알고리즘의 성능 상한이
실제 feedback source에서 어떻게 실현되는지를 확인하였다.
