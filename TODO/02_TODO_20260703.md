# 2026-07-03 Simulator / POMCP 모델링 TODO

## 1. 현재 문제의식

현재 POMCP simulation은 `scripts/planners/simulator.py`를 통해 다음을 수행한다.

```python
next_state = transition_model.sample_next_state(state, action)
observation = observation_model.sample(next_state, action)
reward = reward_model.get_reward(state, action, next_state)
```

구조적으로는 `Simulator`로 분리되었지만, 내부 `transition_model`과 `observation_model`의 일부 도메인 구현은 여전히 `true_state`를 직접 참조한다.

이 경우 POMCP simulation이 sampled particle 또는 belief state 기준으로 미래를 상상하는 것이 아니라, 실제 hidden world를 일부 알고 있는 generative model처럼 동작할 수 있다.

## 2. 목표

POMCP 내부 simulator는 실제 환경의 `true_state`를 직접 보지 않고, 넘겨받은 `state`를 기준으로 다음 상태와 관측을 샘플링해야 한다.

정리하면 다음 구조를 목표로 한다.

```text
POMCP simulation:
  sampled_state, action
  -> model transition
  -> model observation
  -> reward

Real environment:
  true/runtime state, action
  -> real transition
  -> real observation
  -> reward
```

즉, POMCP용 simulator와 실제 environment execution의 의미를 분리한다.

## 3. 우선 합의한 결정

### 3.0 설계 원칙

다음 원칙을 기본으로 둔다.

```text
TransitionModel은 true_state를 참조하지 않는다.
RewardModel은 true_state를 참조하지 않는다.
ObservationModel은 실제 환경 observation을 만들 때 environment / true_state를 참조한다.
```

의미:

- transition은 로봇이 가진 action dynamics model이다. 입력으로 받은 `state`와 `action`만으로 다음 state 분포를 만들어야 한다.
- reward는 `state`, `action`, `next_state`에 대한 task objective 평가다. hidden truth를 직접 보면 안 된다.
- observation은 센서/환경 피드백이다. 실제 실행에서는 당연히 실제 환경을 참조해야 한다.
- 단, POMCP 내부 simulation에서 observation을 샘플링할 때는 실제 `true_state`가 아니라 sampled `state`를 observation reference로 사용해야 한다.

즉 핵심 분리는 다음과 같다.

```text
Transition / Reward:
  always model-based, no true_state access

Observation:
  real execution -> true/environment state reference
  POMCP simulation -> sampled state reference
```

### 3.1 Transition은 우선 공통으로 둔다

당장 `TransitionModel`을 real/model 두 개로 나누지 않는다.

이유:

- transition은 로봇이 어떤 action을 실행했을 때 다음 state가 어떻게 변할지 예측하는 action model이다.
- 따라서 POMCP simulation에서도 실제 execution에서도 의미적으로 같은 transition distribution을 사용한다.
- transition을 real/simulation으로 나누면 같은 action model을 불필요하게 중복 정의하게 된다.
- 분리해야 할 핵심은 transition 자체가 아니라, observation이 실제 `true_state`를 보는지 sampled `state`를 보는지이다.

따라서 1차 목표는 다음이다.

```text
TransitionModel은 공통 사용
RewardModel은 공통 사용
ObservationModel은 POMCP simulation에서 true_state를 보지 않도록 분기
```

### 3.2 Reward도 공통으로 둔다

`RewardModel`도 real/simulation으로 나누지 않는다.

이유:

- reward는 `state`, `action`, `next_state`가 주어졌을 때 그 transition의 가치를 평가하는 함수다.
- POMCP simulation에서든 실제 execution에서든 같은 task objective를 평가해야 한다.
- reward를 real/simulation으로 나누면 같은 목표 함수를 불필요하게 중복 정의하게 된다.
- 따라서 simulator에서 분리해야 할 것은 reward가 아니라 observation의 reference state이다.

## 4. 필요한 구조

`Simulator`에 simulation 목적을 명확히 드러내는 API를 둔다.

예상 구조:

```python
class Simulator:
    def sample(self, state, action):
        # POMCP 내부 black-box generative simulation
        # true_state를 직접 보지 않는 방향
        # returns next_state, observation, reward
        ...
```

원 POMCP 논문 Algorithm 1 기준으로는 `Simulate`뿐 아니라 `Rollout`에서도 simulator `G`를 사용한다.

```text
Rollout:
  a ~ pi_rollout(h, .)
  (s', o, r) ~ G(s, a)
  return r + gamma * Rollout(s', hao, depth + 1)
```

따라서 현재 코드에서도 `simulate()`와 `rollout()` 모두 `Simulator.sample(...)`을 사용한다.

주의:

- rollout에서는 observation을 tree branching에 직접 쓰지 않을 수 있다.
- 그래도 generative model 의미상 `(next_state, observation, reward)`를 함께 샘플링한다.
- 이때 observation은 반드시 sampled state 기준이어야 하며, 실제 `world.true_state`를 참조하면 안 된다.

추후 필요하면 다음처럼 분리할 수 있다.

```python
sample_model(...)
sample_real(...)
```

하지만 현재 `Env.step()`은 그대로 두고, POMCP에서 쓰는 `Simulator.sample()`부터 정리한다.

## 5. Env / SymbolicWorld 분리 방향

현재 `scripts/environments/env.py`는 symbolic environment 역할을 하지만, 여러 책임이 섞여 있다.

현재 `env.py`가 담당하던 책임:

- scene/domain/skill YAML 로드
- 초기 state, hidden true state, goal 생성
- action grounding
- transition / observation / reward model 생성
- 실제 action execution
- true state 갱신
- observation / reward / done 반환

이 중에서 실제 hidden world를 관리하는 책임은 `scripts/environments/world.py`로 분리한다.

목표 구조:

```text
Environment:
  - YAML 로드
  - 모델 생성
  - action step orchestration
  - observation/reward/done 반환

SymbolicWorld:
  - 실제 hidden true_state 보유
  - 실제 action execution 이후 true_state 갱신
  - 도메인별 실제 세계 규칙 관리
```

현재 반영된 1차 구조:

```python
self.world = create_symbolic_world(
    self.domain_name,
    observable_init_state=self.exec_init_state,
    true_init_state=self.gt_init_state,
)
self.true_state = self.world.true_state
```

실제 action 실행 이후에는 `env.py`가 직접 `true_state`를 고치지 않고, world에 위임한다.

```python
self.true_state = self.world.update_after_execution(action, self.state)
```

중요한 의미:

- `SymbolicWorld`의 true state는 `facts`의 공개 초기 상태와 `true_init`의 hidden 상태를 합친 실제 세계다.
- 따라서 `handempty`, `located`, `connected`, type fact 같은 공개 사실도 true world에 포함된다.
- 도메인별 symbolic world 클래스를 명시적으로 둔다.

```text
TomatoWorld
WasteSortingWorld
BlocksWorld
KitchenWorld
RoverWorld
WateringWorld
```

1차 구현에서는 도메인별 클래스가 공통 갱신 규칙을 공유한다. 이후 도메인마다 실제 세계 갱신 규칙이 달라지면 각 클래스의 `after_action(...)` hook에 추가한다.

주의할 점:

- 이 분리는 `env.py`의 true world 관리 책임을 정리하기 위한 것이다.
- POMCP planner logic, tree pruning, 평가 방식은 바꾸지 않는다.
- 현재 `TransitionModel`과 각 도메인 `trans.py`는 `true_state`를 직접 받지 않도록 정리했다.

## 6. ObservationModel 수정 방향

`ObservationModel.sample()`이 `use_true_state` 또는 `mode`를 받을 수 있게 한다.

예상 형태:

```python
observation_model.sample(
    state=next_state,
    action=action,
    use_true_state=False,
)
```

의미:

- `use_true_state=True`: 실제 환경 실행용 observation
- `use_true_state=False`: POMCP simulation / belief particle 기준 observation

현재 일부 도메인 obs에는 이미 비슷한 구조가 있다.

예:

- `get_observation_distribution_for_likelihood(...)`
- 도메인별 `_build_*_distribution(..., use_true_state=False)`

이걸 `sample()` 경로에서도 활용하는 방향이 자연스럽다.

## 8. Watering 도메인에서 특히 조심할 점

Watering의 `find_basket`, `find_plant`는 현재 실제 hidden 위치를 `true_state`에서 직접 확인하는 구조다.

정석 POMDP 구조에서는 다음과 같아야 한다.

```text
sampled particle says plant1 is in room2
-> find_plant(room2)는 성공할 수 있음

sampled particle says plant1 is in room1
-> find_plant(room2)는 실패하거나 false positive만 가능
```

즉 POMCP simulation에서는 `true_state`가 아니라 sampled `state` 기준으로 observation likelihood가 만들어져야 한다.

## 9. 구현 순서

1. `ObservationModel.sample()`에 `use_true_state` 옵션 추가
2. 각 도메인 observation wrapper에서 이 옵션을 도메인 obs로 전달
3. `Simulator.sample()`에서는 `use_true_state=False`로 observation sample
4. `Env.step()`에서는 기존 동작 유지 또는 명시적으로 `use_true_state=True` 사용
5. Tomato / watering에서 simulation observation이 particle 기준으로 동작하는지 확인
6. Transition / reward 구현이 `true_state`를 직접 참조하지 않는지 점검하고, 참조가 있으면 입력 `state` 기준으로 고친다.

## 12. 현재 main.py 기준 파일별 실행 흐름

아래는 현재 코드 기준으로 `main.py`를 실행했을 때의 큰 흐름이다.

### 12.1 main.py

`main.py`는 전체 실험 loop를 조율한다.

주요 순서:

```text
1. parse_args(...)
2. Environment(args) 생성
3. BeliefManager(...) 생성
4. POMCPPlanner(...) 생성
5. env.reset()
6. belief 초기화
7. while not done:
   7-1. planner.search(belief)
```

즉 `main.py`는 직접 transition, observation, reward를 계산하지 않는다. 각 모듈을 호출해서 한 step의 planning, execution, belief update, query, done check를 순서대로 실행한다.

초기화 단계에서 하는 일:

- `TransitionModel`, `ObservationModel`, `RewardModel` 생성

현재 상태 구분:

```text
self.state

self.world.true_state
  - 실제 hidden symbolic world state
  - facts + true_init을 합친 실제 세계 상태
```

### 12.4 scripts/models/transition.py + 각 도메인 trans.py

`TransitionModel`은 action이 주어졌을 때 가능한 next state 후보를 만든다.

주요 API:

```python
sample_next_state(state, action)
get_next_state_distribution(state, action)
```

현재 쓰임:

- `env.step(...)`에서는 실제 실행 next state를 샘플링할 때 사용
- `BeliefManager.update_belief(...)`에서는 가능한 frontier 후보를 만들 때 사용
- `Simulator.sample(...)`에서는 POMCP 내부 simulation 후보를 만들 때 사용

주의:

- 설계 원칙상 transition은 true state를 직접 참조하지 않는 방향이 맞다.
- 하지만 현재 일부 도메인 `trans.py`는 아직 `true_state` 참조가 남아 있다.
- 이 부분은 이후 별도 정리 대상이다.

### 12.5 scripts/models/observation.py + 각 도메인 obs.py

`ObservationModel`은 observation distribution과 likelihood를 담당한다.

현재 쓰임:

```text
Real execution:
  env.step(...)
  -> observation_model.sample(..., use_true_state=True)
  -> 실제 world.true_state 기준 observation 가능

Belief update:
  belief_manager.update_belief(...)
  -> observation_model.likelihood(obs, candidate_state, action)
  -> candidate frontier state 기준 likelihood 평가

POMCP simulator:
  현재는 observation_model을 직접 사용하지 않음
```

현재 `Simulator`에서는 observation을 domain `obs.py`에서 샘플링하지 않고, transition이 만든 next state 후보를 그대로 `Observation(next_state.copy())`로 사용한다.

### 12.6 scripts/models/reward.py + 각 도메인 rw.py

`RewardModel`은 `state`, `action`, `next_state`를 기준으로 reward를 계산한다.

현재 쓰임:

- `env.step(...)`에서 실제 action reward 계산
- `Simulator.sample(...)`에서 POMCP 내부 simulation reward 계산

설계 원칙:

```text
RewardModel은 true_state를 직접 참조하지 않는다.
RewardModel은 state/action/next_state 기준으로만 평가한다.
```

### 12.7 scripts/models/belief_update.py

`BeliefManager`는 실제 observation 이후 belief를 갱신한다.

`update_belief(belief, obs, action)` 흐름:

```text
1. 현재 belief.knowledge에서 transition 후보 생성
2. 후보가 너무 많으면 max_belief_particles 기준으로 sampling
3. 각 candidate next_state에 대해:
   - transition probability
   - observation likelihood 계산
4. posterior ∝ transition_prob * observation_likelihood
5. frontier particles + weights 저장
6. fluent 정보 병합
```

중요한 점:

- belief update는 실제 `world.true_state`를 직접 보면 안 된다.
- 실제 observation `obs`는 env에서 온 값이다.
- candidate state별 likelihood는 observation model의 likelihood 경로에서 계산한다.

### 12.8 scripts/planners/pomcp.py

`POMCPPlanner`는 현재 belief에서 action을 선택한다.

초기화:

```text
env.actions
belief_manager.transition_model
belief_manager.observation_model
env.reward_model
Simulator(transition_model, reward_model)
POMDPTree
```

`search(belief)` 흐름:

```text
1. root history 설정
2. root knowledge 설정
3. n_simulations만큼:
   - root particle sampling
   - simulate(sampled_root_state, root_history, depth=0)
4. root action value 기준 best action 선택
```

`simulate(state, history, depth)` 흐름:

```text
1. depth / discount cutoff 확인
2. applicable action 확인
3. leaf node이면 action children 확장 후 rollout
4. leaf가 아니면 UCB로 action 선택
5. self.simulator.sample(state, action)
6. observation node로 이동
7. recursive simulate
8. tree visit/value 업데이트
```

`rollout(state, depth)` 흐름:

```text
1. depth / discount cutoff 확인
2. random applicable action 선택
3. self.simulator.sample(state, action)
4. reward + gamma * rollout(next_state, depth+1)
```

원 POMCP 논문 기준으로 rollout도 simulator를 사용한다.

### 12.9 scripts/planners/simulator.py

`Simulator`는 POMCP 내부 planning 전용 generative model이다.

현재 `Simulator.sample(state, action)` 흐름:

```text
1. transition_model.get_next_state_distribution(state, action)
2. transition probability를 weight로 candidate next_state 샘플링
3. observation = Observation(next_state.copy())
4. reward_model.get_reward(state, action, next_state)
5. SimulationStep(next_state, observation, reward) 반환
```

중요한 설계:

- `Simulator`는 `world.py`를 사용하지 않는다.
- `Simulator`는 실제 `world.true_state`를 보지 않는다.
- `Simulator`는 현재 `ObservationModel`도 직접 사용하지 않는다.
- observation은 transition 후보에서 선택된 next state를 그대로 symbolic observation으로 사용한다.

즉 현재 POMCP 내부 simulation은 다음처럼 단순화되어 있다.

```text
sampled_state, action
-> transition distribution
-> weighted random next_state
-> observation := next_state
-> reward(state, action, next_state)
```

### 12.10 scripts/planners/tree.py

`POMDPTree`는 POMCP search tree를 관리한다.

역할:

- history node 저장
- action child / observation child 생성
- visit count 저장
- value 업데이트
- particle 저장
- 실제 action/observation 이후 tree pruning

현재 `main.py`에서는 real step 이후:

```python
planner.prune_search_tree(action=action, obs=belief.knowledge)
```

를 호출한다.

즉 실제 environment observation 자체가 아니라, query/feedback까지 반영된 최종 belief knowledge를 기준으로 tree를 자른다.

### 12.11 한 step의 전체 데이터 흐름 요약

```text
main.py
  -> planner.search(belief)
      -> pomcp.py
          -> simulator.py
              -> transition.py / rw.py
          -> tree.py update

  -> env.step(action)
      -> transition.py
      -> world.py update
      -> observation.py / obs.py with use_true_state=True
      -> reward.py / rw.py

  -> belief_manager.update_belief(belief, observation, action)
      -> transition.py
      -> observation.py likelihood
      -> belief frontier update

  -> feedback_manager.get_new_observation(...)
      -> query / oracle / auto answer
      -> belief knowledge refinement

  -> env.check_done(belief)
      -> check_done.py

  -> planner.prune_search_tree(action, belief.knowledge)
      -> tree.py
```

### 12.12 현재 책임 분리 기준

```text
Real Environment:
  env.py + world.py + observation.py/obs.py

POMCP Internal Simulation:
  pomcp.py + simulator.py + transition.py + reward.py

Belief Update:
  belief_update.py + transition.py + observation.py likelihood

Goal / Failure Judgment:
  check_done.py
```

앞으로 구조를 바꿀 때는 이 기준을 유지한다.

## 13. 다음 작업: 도메인별 symbolic dynamics 정교화

현재 큰 구조는 어느 정도 분리되었다.

현재 상태:

```text
POMCP:
  모든 도메인에서 Simulator 사용

Simulator:
  world.py / true_state / obs.py 직접 참조 없음
  transition distribution에서 next_state를 확률대로 샘플링
  observation := next_state
  reward(state, action, next_state)

Real Environment:
  env.py + world.py + obs.py가 실제 observation 담당
```

현재 POMCP simulation 경로는 transition 기준으로 `true_state-free`가 되도록 정리했다.

```text
Simulator
  -> TransitionModel
      -> 각 도메인 trans.py
```

위 경로에서 `true_state` / `world.true_state`를 직접 참조하지 않는다.

따라서 앞으로의 핵심 작업은 시스템 구조보다 **각 도메인의 sampled-state 기반 symbolic dynamics를 더 정교화하는 것**이다.

### 13.1 핵심 원칙

```text
world.py / obs.py:
  실제 환경을 정교하게 만든다.
  실제 observation은 world.true_state를 참조할 수 있다.

trans.py:
  planner가 상상할 수 있는 sampled-state / belief-state 기반 dynamics를 만든다.
  true_state를 직접 참조하지 않는다.

rw.py:
  true_state 없이 state/action/next_state 기준으로 goal progress를 평가한다.

simulator.py:
  도메인 로직을 직접 갖지 않는다.
  transition 후보를 확률대로 샘플링한다.
```

### 13.2 도메인별 정리 우선순위

1. `wastesorting`
   - category detection / placement 관련 transition 품질 점검
   - 현재 sampled state에 포함된 category belief/fact가 있을 때 그 정보를 잘 활용하는지 확인

2. `watering`
   - `find_basket`, `find_plant`의 sampled-state 기반 location 후보 품질 점검
   - 없는 basket/plant가 반복 생성되지 않도록 상태 일관성 유지

3. `kitchen`
   - `open_fridge`, `inspect_*` 관련 clean/dirty/in_fridge 후보 품질 점검
   - sampled state 기준 ingredient/pot 상태 후보가 너무 낙관적이지 않은지 확인

4. `rover`
   - `detect_road`, `detect_soil`, visibility/soil 후보 품질 점검
   - sampled map/terrain state 기준 탐지 결과가 너무 넓거나 좁지 않은지 확인

5. `tomato`
   - detect/scan의 coarse observation과 semantic predicate 충돌 정리

6. `blocksworld`
   - deterministic/full-observable 성격이 강하므로 가장 단순
   - 현재 transition은 true_state 없이 동작

### 13.3 목표 상태

최종 목표:

```text
POMCP simulation path:
  pomcp.py
  -> simulator.py
  -> transition.py / domain trans.py
  -> reward.py / domain rw.py

위 경로에서는 true_state / world.true_state를 직접 참조하지 않는다.
```

반면 실제 환경 실행 경로는 다음을 유지한다.

```text
Real execution path:
  main.py
  -> env.step(action)
  -> transition.py
  -> world.py update
  -> observation.py / domain obs.py with world.true_state
  -> reward.py
```

즉 앞으로는 “planner가 상상하는 세계”와 “실제 환경이 관측하는 세계”를 도메인별로 더 정교하게 분리한다.
