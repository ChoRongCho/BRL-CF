# 2026-07-04 POMCP Sensing Value Bias TODO

## 1. 문제 정의

현재 POMCP simulation에서 hidden object location을 모르는 상태일 때, 특정 장소에서의 sensing action value가 과도하게 높게 나오는 현상이 있다.

Watering 예시는 다음과 같다.

```text
robot is at tap
basket location unknown
plant location unknown
goal reward is sparse
```

이 상태에서 planner는 실제 환경에서 basket이나 plant가 어디 있는지 모른다. 그러나 simulation 내부 transition은 `find_basket(robot,tap)` 또는 `find_plant(robot,tap)`을 수행했을 때, sampled state 안에서 object가 tap에 있다고 가정되는 outcome을 만들 수 있다.

`tap`은 물을 채울 수 있는 장소이므로, object가 tap에 있다고 가정되는 순간 reward path가 매우 짧아진다.

```text
find_basket at tap
-> pick_basket at tap
-> load_water at tap
-> find/pour plant near current path
-> goal reward
```

즉 tap이 실제로 정답일 가능성이 높아서 value가 커지는 것이 아니다. Simulation 안에서 tap이라는 장소가 가장 짧은 optimistic reward path를 만들 수 있기 때문에, tap에서의 find action value가 커진다.

## 2. 일반화

이 현상은 watering에만 국한되지 않는다.

일반적으로 다음 조건이 동시에 있으면 발생할 수 있다.

```text
1. 중요한 object/location이 partially observable이다.
2. sensing action이 현재 장소에서 object 존재 가능성을 열어준다.
3. 어떤 장소가 goal 달성에 필요한 핵심 resource/action hub이다.
4. reward가 sparse해서 최종 goal reward만 크다.
5. simulation rollout이 실제 hidden truth가 아니라 sampled optimistic state를 따라간다.
```

그러면 planner는 실제로 그 장소에 object가 있는지 모르는 상태에서도, 그 장소에서 object가 발견되는 branch가 goal까지 짧게 이어지기 때문에 sensing action을 높게 평가할 수 있다.

이를 일반적으로 다음과 같이 부를 수 있다.

```text
optimistic sensing value inflation
```

또는 더 구체적으로:

```text
hub-location optimistic discovery bias
```

의미:

- `hub-location`: goal 달성에 필요한 resource/action이 모이는 장소
- `optimistic discovery`: simulation에서 미지 object가 그 장소에서 발견될 수 있는 branch
- `bias`: 실제 posterior evidence가 충분하지 않아도 그 branch가 큰 value를 만들어 action 선택을 왜곡함

## 3. Watering에서의 구체적 증상

Watering에서 `tap`은 특수한 장소다.

```yaml
load_water:
  preconditions:
    - tap(T)
    - at(A,T)
    - holding(A,C)
```

따라서 robot이 tap에 있는 상태에서 basket이 tap에 있다고 simulation되면, `pick_basket -> load_water`까지 매우 짧다.

또 plant도 tap에 있다고 simulation되면, `pour_water`까지도 짧아진다.

결과적으로 POMCP value는 다음처럼 튈 수 있다.

```text
find_basket(robot,tap): high value
find_plant(robot,tap): high value
```

이 value는 다음을 의미하지 않는다.

```text
tap에 basket/plant가 있을 확률이 높다.
```

더 정확한 의미는 다음이다.

```text
tap에서 발견된다고 가정되는 simulation branch가 goal reward까지 짧고 크다.
```

## 4. Negative information과는 다른 문제

이 문제는 단순히 negative reward가 없어서 생기는 문제가 아니다.

초기 문제 분석 시점에는 모든 room에서 실패한 sensing에 별도 penalty가 없었다. 이후 실험에서는 empty find action에 penalty를 추가할 수 있지만, 그 경우에도 핵심은 penalty 유무 자체보다 hub location에서 발견 branch가 goal reward까지 짧게 이어지는 구조다.

핵심은 다음 차이다.

```text
일반 room:
  object를 발견해도 tap으로 이동해서 물을 채우는 등 추가 horizon이 길다.

tap:
  object를 발견하면 load_water와 이어지는 핵심 precondition이 이미 가까이 있다.
```

따라서 value 차이는 reward penalty 때문이 아니라, sampled future에서 goal reward까지의 path length와 success branch 구조 때문에 생긴다.

## 5. 왜 반복 find로 보이는가

실제 execution에서 `find_plant(robot,tap)` 후 observation이 empty이고 oracle query가 `at(plant,tap)=False`라고 답해도, 현재 symbolic knowledge에는 다음 형태의 negative fact가 명시적으로 남지 않는다.

```text
not at(plant1,tap)
not at(plant2,tap)
not at(basket1,tap)
```

즉 knowledge diff는 비어 있을 수 있다.

```text
+ add (0): -
- del (0): -
```

이 경우 planner의 다음 simulation은 여전히 미지 object가 tap에서 발견되는 branch를 만들 수 있다. 그래서 같은 장소에서 find action이 반복적으로 높은 value를 가질 수 있다.

단, 이 현상은 negative fact 저장만의 문제가 아니다. Negative fact를 저장하더라도, 다른 hub location이 있으면 같은 구조의 optimistic discovery bias가 다른 장소에서 나타날 수 있다.

## 6. 설계적으로 점검할 질문

해결책을 바로 넣기 전에 다음을 구분해야 한다.

```text
Q1. POMCP state representation이 negative location evidence를 표현해야 하는가?
Q2. sensing action은 한 장소에서 object 존재 가능성을 어떻게 업데이트해야 하는가?
Q3. rollout policy가 sparse reward에서 너무 optimistic branch에 의존하고 있지 않은가?
Q4. hub location에서 discovery branch가 value를 과도하게 만드는 것을 어떻게 완화할 것인가?
```

가능한 방향은 여러 가지다.

```text
1. Negative location evidence를 belief/state에 명시적으로 표현한다.
2. Observation likelihood만으로 negative evidence를 frontier에 반영하되, knowledge에는 올리지 않는다.
3. Rollout policy를 random이 아니라 goal-directed but belief-aware하게 바꾼다.
4. Sensing action value를 information gain과 task value로 분리해서 분석한다.
5. Hub location optimistic discovery가 생기는 도메인 구조를 실험 로그에서 별도 지표로 기록한다.
```

이 중 어느 방향을 채택할지는 별도 설계 결정이 필요하다. 임의로 marker fact를 추가하거나 POMCP applicable action을 직접 필터링하는 방식은 상태 의미를 바꾸므로 신중해야 한다.

## 7. 현재 결론

현재 watering에서 `tap`의 `find_basket`, `find_plant` value가 크게 나오는 핵심 원인은 다음이다.

```text
tap is a reward-path hub.
unknown object discovery at tap creates a short optimistic path to sparse goal reward.
POMCP simulation can sample that optimistic branch.
therefore find actions at tap receive inflated value.
```

이를 watering 특수 버그로만 보지 말고, partially observable task planning에서 발생할 수 있는 일반적인 sensing value bias로 다루어야 한다.

## 9. POMCP / belief 관련 현재 의도

요구한 의도는 다음이었다.

```text
search / simulate / rollout:
  belief particle 전체를 유지해서 POMCP 내부 시뮬레이션에 사용한다.

actual execution / update:
  실제 action 수행 후에는 certain knowledge 기준으로 update한다.
  이전 action의 frontier_weights를 다음 action의 prior로 계속 끌고 가지 않는다.
  feedback/query가 끝나면 하나의 MAP symbolic state로 collapse한다.
```

현재 코드에서 이를 위해 바뀐 부분:

```text
pomcp.py:
  root simulation state를 belief.frontier/frontier_weights에서 sampling한다.
  backup 대비 의도된 차이는 root particle sampling 부분이어야 한다.

belief_update.py:
  update_belief는 belief.knowledge에서 해당 action의 local frontier를 새로 만든다.
  weights = transition probability * observation likelihood 로 계산한다.
  이전 belief.frontier를 prior로 다시 전개하지 않는다.

feedback_manager.py:
  질문 후 max frontier를 belief.knowledge로 선택한다.
  이후 belief.reset_belief()로 frontier를 single certain state로 접는다.
```

직접 확인할 점:

```text
1. pomcp.py와 pomcp_backup.py의 차이가 root belief sampling 외에 없는지.
2. profile_search logging 코드가 backup과 동일한지.
3. feedback_manager.py의 reset_belief()가 원하는 시점에만 호출되는지.
4. main.py의 check_done/prune_search_tree가 항상 collapsed belief.knowledge를 사용하는지.
```
