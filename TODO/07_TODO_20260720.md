# 2026-07-22 앞으로의 연구 및 구현 계획

## 1. 현재 논문 방향

논문은 HRI 자체보다 **부분 관측 환경에서 symbolic uncertainty를 관리하는 로봇
의사결정 시스템**에 초점을 둔다.

중심 문제:

```text
로봇은 부분 관측 환경에서 여러 symbolic world hypothesis를 유지한다.
로봇은 posterior belief가 충분히 확실한지 판단하여 피드백이 필요한 시점을 정한다.
피드백이 필요하면 전체 state나 다음 action을 요청하지 않고,
현재 hypothesis를 구분하는 구체적인 grounded fact를 선택해 확인한다.
응답은 belief와 knowledge base에 반영되고 이후 planning이 계속된다.
```

현재 방법은 human query를 POMDP action space에 넣어 physical action과 공동
최적화하는 Targeted Query POMDP가 아니다.

```text
POMDP planner:
  physical/sensing action을 선택

Corrective query layer:
  action 실행 후 belief uncertainty 평가
  → 언제 물을지 결정
  → 무엇을 물을지 결정
  → answer로 belief filtering
  → knowledge commitment 및 replanning
```

현재 논문의 핵심 두 축:

```text
When:
  belief entropy/confidence에 기반해 질문 시점 결정

What:
  knowledge base의 grounded fact 중
  현재 symbolic hypotheses를 가장 잘 구분하는 fact 선택
```

## 3. Contribution 초안

### 3.1 Contribution 1 — When to ask

```text
We introduce a belief-entropy-based query trigger that enables a robot
to autonomously determine when external verification is required during
partially observable task execution.
```

한국어:

```text
부분 관측 task 실행 중 posterior belief의 entropy를 평가하여,
현재 symbolic state를 확정하기 어려울 때만 외부 검증을 요청하는
자율적 질의 시점 결정 방법을 제안한다.
```

구현 근거:

```text
Conf(B) = 1 - H(B) / log2|B|

Conf(B) < τ:
  query

Conf(B) ≥ τ:
  MAP hypothesis를 knowledge state로 commit
```

검증 질문:

- No Query보다 task failure를 줄이는가?
- Always Query보다 적은 질문으로 성공률을 유지하는가?
- Random timing보다 안정적인가?
- Threshold 변화에 success-query trade-off가 어떻게 나타나는가?

### 3.2 Contribution 2 — What to ask

```text
We introduce a knowledge-grounded query selection method that asks for
the truth value of a specific symbolic fact rather than requesting the
complete state or delegating the next action decision to the user.
```

한국어:

```text
전체 state나 다음 robot action을 요청하지 않고,
현재 competing symbolic worlds를 가장 효과적으로 구분하는
grounded predicate fact를 knowledge base에서 선택하는 방법을 제안한다.
```

현재 선택 기준:

```text
c* = argmin_c [
  P(c) H(B_c^+) + P(not c) H(B_c^-)
]
```

검증 질문:

- Random fact보다 query당 entropy 감소량이 큰가?
- 동일 query budget에서 task success가 높은가?
- Full-state oracle보다 제한된 정보를 사용하면서 실용적인 성능을 내는가?
- KnowNo-style action query보다 underlying state uncertainty를 안정적으로 해소하는가?

주의:

현재 구현이 직접 보장하는 것은 `task-relevant fact` 전체가 아니라 **현재
action-induced frontier를 구분하는 informative fact**다. Goal이나 future action
precondition과의 relevance를 주장하려면 별도 dependency filtering이 필요하다.

### 3.3 Contribution 3 후보 — How framing

`When / What / How`를 유지하려면 `How`가 앞의 두 항목과 겹치지 않아야 한다.

#### 후보 A — How to incorporate feedback into planning

```text
How:
  선택한 fact의 answer를 belief filtering과 knowledge commitment에 반영하고,
  갱신된 symbolic state로 replanning하는 closed-loop execution 방법
```

영문 초안:

```text
We develop a closed-loop knowledge refinement pipeline that incorporates
predicate-level feedback into the symbolic belief, commits sufficiently
resolved knowledge, and continues online planning and execution.
```

흐름:

```text
physical action
→ observation
→ symbolic frontier
→ Bayesian weighting
→ uncertainty trigger
→ fact query
→ belief filtering
→ knowledge commitment
→ replanning
```

장점:

- `When`, `What` 다음에 “그 답을 planning에 어떻게 사용하는가”로 자연스럽게 연결됨
- HRI보다 system architecture contribution으로 설명 가능
- 현재 구현과 real-robot pipeline을 포괄함

위험:

- 단순 module integration으로 보이면 algorithmic novelty가 약할 수 있음
- Belief filtering과 replanning 자체는 알려진 방법이라는 반론 가능
- 독립 contribution보다는 system contribution으로 묶는 편이 자연스러울 수 있음

#### 후보 B — How to ask: state-level fact verification

```text
How:
  action decision을 사용자에게 넘기지 않고,
  사람이 직접 확인 가능한 state-level fact의 yes/no verification으로 질문
```

비교:

```text
Action-level:
  "다음에 어떤 행동을 해야 하는가?"

State-level:
  "ripe(tomato1)가 참인가?"
```

장점:

- KnowNo와의 비교가 명확함
- 기존 user study 자료와 연결 가능

위험:

- `What to ask`와 거의 같은 주장으로 보임
- 다시 HRI/workload 중심으로 논문이 이동할 수 있음
- 시스템 논문 방향과는 후보 A보다 덜 맞음

#### 후보 C — How to generalize across tasks

```text
How:
  domain-specific predicate/action model만 교체하고
  동일한 uncertainty-trigger/query-selection loop를 재사용하는 방법
```

영문 초안:

```text
We present a reusable system architecture that connects symbolic task
models, particle beliefs, perception, and corrective fact verification,
and demonstrate it across distinct robotic domains and a physical robot.
```

장점:

- HRI가 아닌 system contribution으로 가장 명확함
- Waste sorting, tomato harvesting, scale, real robot 결과와 연결됨

위험:

- “How”라는 단어에 억지로 맞춘 느낌이 남음
- 두 domain만으로 generality를 강하게 주장하면 과장으로 보일 수 있음

### 3.4 추천 framing

현재 방향에서는 `When / What / How`보다 다음 구성이 더 안전하다.

```text
1. When:
   Belief-entropy-based query triggering

2. What:
   Knowledge-grounded fact query selection

3. System:
   Closed-loop integration of symbolic knowledge, belief refinement,
   planning, perception, and corrective feedback
```

그래도 `When / What / How`를 유지한다면 후보 A가 가장 자연스럽다.

```text
When:
  언제 외부 검증이 필요한가?

What:
  어떤 symbolic fact를 검증해야 하는가?

How:
  그 검증 결과를 belief와 KB에 어떻게 반영하여 planning을 계속하는가?
```

최종 결정 전 확인할 것:

- [ ] How가 독립적인 실험과 metric을 가질 수 있는가?
- [ ] How를 제거해도 논문의 핵심 algorithm 설명이 완전한가?
- [ ] Reviewer가 integration만으로 contribution을 인정할 근거가 충분한가?
- [ ] Real robot과 cross-domain 결과가 system contribution을 지지하는가?

## 4. 전체 실험 Master Plan

### 4.1 Research question 매핑

```text
RQ1 — When:
  Entropy trigger가 질문 수와 task success의 trade-off를 개선하는가?

RQ2 — What:
  Informative grounded-fact selection이 다른 query content보다 효과적인가?

RQ3 — System:
  동일한 closed-loop query framework가 서로 다른 domain과 scale에서 작동하는가?

RQ4 — Feasibility:
  실제 사용자가 simulation 중 생성되는 fact query에 응답할 수 있는가?
```

### 4.2 핵심 비교 조건

| Method | When | What | 목적 |
|---|---|---|---|
| No Query | Never | 없음 | Feedback 없는 하한 |
| Always | 모든 ambiguity | Ours fact selector | 질문 상한 및 interaction cost |
| Random-When | Random timing | Ours fact selector | When ablation |
| Random-What | Ours entropy trigger | Random fact | What ablation |
| Most-Uncertain | Ours entropy trigger | `P(c)≈0.5` fact | 단순 uncertainty baseline |
| KnowNo | Conformal trigger | Action-level options | 외부 action-query baseline |
| Ours | Entropy trigger | Expected-entropy fact | 전체 제안법 |

Optional/upper bound:

```text
Full-State Oracle:
  질문 한 번에 correct world 전체 제공

Joint Query-POMDP:
  ask action을 POMDP action space에 넣어 task/query를 공동 최적화
```

`Joint Query-POMDP`는 현재 연구 목표와 다르므로 main baseline의 필수 조건이 아니다.
구현한다면 가장 가까운 prior architecture와의 선택적 비교로 사용한다.

### 4.3 When 실험

고정:

```text
What = Ours expected-entropy fact selector
Feedback = oracle
```

비교:

```text
No / Always / Random-When / Ours
Threshold sweep
```

지표:

- Success rate
- Query count/rate
- Query probability per step
- Planning length
- Dead-end/failure rate
- Final belief entropy
- Execution time

### 4.4 What 실험

고정:

```text
When = Ours entropy trigger
Feedback = oracle
Query budget 또는 trigger point 동일
```

비교:

```text
Random-What
Most-Uncertain Fact
Expected-Entropy Fact (Ours)
KnowNo Action Query
Full-State Oracle (upper bound)
```

지표:

- Success rate
- Information gain per query
- Frontier size before/after query
- Correct-world survival rate
- Repeated query count
- Query count
- Invalid/dead-end action rate

### 4.5 System/generalization 실험

Domain:

```text
Waste sorting
Tomato harvesting
```

Scale:

```text
Standard: 4 objects
Scaled: 6 objects
가능하면 추가 object scale
```

검증할 공통 요소:

```text
동일 entropy trigger
동일 fact-selection equation
동일 belief filtering
동일 planning loop
```

Domain-specific 요소:

```text
Predicate vocabulary
Transition/observation model
Robot skill
Question template
```

지표:

- Success degradation by scale
- Query-rate change
- Planning/search time
- Belief frontier size
- Memory/particle count
- Domain adaptation에 필요한 코드/config 변경량

### 4.6 Feedback robustness — 보조 실험

```text
oracle
noisy-oracle error-rate sweep
human-proxy
human pilot
```

이 실험은 contribution이 아니라 robustness/feasibility 분석으로 둔다.

## 5. Active Search Baseline 구현 및 평가

### 5.1 구현 목적

Active Search baseline의 목적은 단순히 다른 POMDP solver를 구현하는 것이 아니다.

```text
우리 방식:
  physical planner 실행 후 corrective query layer에서 ambiguity 해소

비교 방식:
  information acquisition을 planning objective/action 안에서 직접 고려
```

이를 통해 확인할 질문:

- Query를 planner action에 포함해야만 좋은 성능을 얻는가?
- 분리된 corrective layer가 더 단순한 계산으로 비슷한 task performance를 내는가?
- Action space 확대에 따른 planning cost는 얼마인가?

### 5.2 먼저 결정할 baseline 범위

후보 1 — Targeted Query POMDP:

```text
Physical action ∪ ask(object, property)
Query answer를 observation으로 모델링
Query cost를 reward에 포함
```

후보 2 — ρ-POMDP information reward:

```text
Belief-dependent information reward
Physical/sensing action의 future belief value 평가
```

후보 3 — Active Inference information gathering:

```text
EFE 기반 information-gathering action selection
```

우선순위:

```text
1. 현재 구현된 ρ-POMDP code의 correctness 확인
2. Human ask action을 포함할지 여부를 baseline 정의와 함께 확정
3. Targeted Query POMDP는 optional closest-prior baseline으로 판단
4. Active Inference 전체 재현은 시간 대비 필요성을 다시 평가
```

주의:

Targeted Query POMDP가 현재 논문의 목표인 것처럼 서술하지 않는다. 이는 query를
planning action으로 공동 최적화하는 다른 architecture다.

### 5.3 공정한 비교 조건

- 동일 domain/scene
- 동일 initial belief
- 동일 transition/observation model
- 동일 feedback accuracy
- 동일 success criterion
- 동일 maximum step
- 가능하면 동일 wall-clock 또는 simulation budget
- Query cost/budget을 명시적으로 보고

추가 로그:

- Expanded belief/action nodes
- Grounded action 수
- Search depth
- Planning wall-clock time
- Query action 수
- Timeout rate
- Peak particle/frontier size

## 6. 사용자 평가용 Simulation 및 Interface

### 6.1 평가 목적

HRI superiority를 강하게 주장하지 않는다. 우선 목적은 다음 feasibility 확인이다.

```text
Planner가 실행 중 자유롭게 생성한 fact query를
실제 사용자가 이해하고 응답할 수 있는가?

응답이 simulation, belief update, replanning과
안정적으로 연결되는가?
```

### 6.2 필요한 실행 흐름

```text
Simulation
→ physical action 실행
→ observation 및 belief update
→ query trigger
→ selected fact를 UI에 표시
→ simulation pause
→ 사용자 answer
→ belief filtering
→ replanning
→ simulation resume
```

### 6.3 Interface 기능

- [ ] WasteSorting/Tomato scene 표시
- [ ] Query target object highlight
- [ ] Symbolic fact를 자연스러운 문장으로 변환
- [ ] Yes / No / Unknown 또는 응답 불가 입력
- [ ] 응답 전 simulation pause
- [ ] 응답 후 deterministic resume
- [ ] 현재 step/action/query 표시 여부 결정
- [ ] Timeout 및 잘못된 입력 처리
- [ ] 동일 seed replay

### 6.4 Logging

- Participant/session ID
- Domain/scene/seed
- Physical action history
- Query fact와 natural-language question
- Entropy/confidence before/after
- User answer와 oracle answer
- Response time
- Timeout/no-answer
- Task success/failure
- Query count
- Total operation time

### 6.5 평가 단계

```text
Stage 1:
  개발자 내부 dry run

Stage 2:
  1명 think-aloud pilot

Stage 3:
  3명 interface/protocol pilot

Stage 4:
  필요할 경우 5~6명 feasibility evaluation
```

5~6명 결과로 workload 우월성이나 일반적인 HRI 결론을 강하게 주장하지 않는다.
